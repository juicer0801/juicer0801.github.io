卡巴斯基拦截 DSH：故障分诊与解决指南

DSH（DeepSeek Harness）在日常使用中可能触发卡巴斯基的两种不同拦截。它们的表现、根因和解决路径各不相同，但共同点是卡巴斯基给出的提示信息很少，用户往往需要自行完成大部分诊断工作。本文按“先分诊、再处置”的顺序，分别说明两类拦截的识别方法和配置步骤。

第一步：分清你遇到的是哪一种拦截

DSH 被卡巴斯基影响时，通常表现为以下两种形态之一：

形态 A：显式报毒。 卡巴斯基弹出启发式检测提示，可能包含 PDM:Trojan.Win32.Generic 或类似的通用威胁名称。DSH 进程被终止，或相关文件被隔离。

形态 B：静默的 TLS 失败。 卡巴斯基不弹窗，DSH 界面上只显示 transport failed 或 502。翻查日志才能看到真正的错误码：SELF_SIGNED_CERT_IN_CHAIN、UNABLE_TO_VERIFY_LEAF_SIGNATURE 等 TLS 信任错误。

两者的区别在于：形态 A 卡巴斯基至少告诉了你“我拦了”；形态 B 则什么也不说，DSH 只是在 TLS 握手阶段被卡巴斯基的中间人证书挡住，错误被 Node 的 fetch 包装成一条泛泛的传输失败。

第二步：处理 TLS 拦截（形态 B）

根因是两套信任栈的错位。卡巴斯基的“加密连接扫描”开启后，会对 HTTPS 流量做中间人重签，用自己的根证书替换原始证书链。浏览器信任它，因为卡巴斯基的根证书被写入了 Windows 系统证书库。但 Node.js 的 fetch 不读系统证书库，只认自己内置的 CA bundle 和 NODE_EXTRA_CA_CERTS 指定的额外证书。两边对不上，握手就死在这里。

有三种解法，推荐程度从高到低。

解法一：让 Node 读取系统证书库（推荐，单变量）

设置环境变量，使 Node.js 信任操作系统证书库中已有的根证书：

Windows 下在系统环境变量中新建 NODE_USE_SYSTEM_CA，值为 1，然后重启 DSH。这不会降低 TLS 校验强度，只是把信任源从 Node 内置列表切换到系统列表，而卡巴斯基的根证书本来就在系统列表中。

解法二：显式导出卡巴斯基根证书，通过 NODE_EXTRA_CA_CERTS 注入

如果不想改变全局的信任策略，可以把卡巴斯基的根证书单独导出为 PEM 文件，只让 Node 额外信任这一张证书。卡巴斯基自己的产品文档中也使用了这一机制，示例路径为 KL_Root.pem。

操作步骤：

  1. 在卡巴斯基界面或 Windows 证书管理器中找到 Kaspersky Anti-Virus Personal Root Certificate；

解法三：在卡巴斯基侧排除目标域名（DSH 零改动）

如果不想在 Node 侧做任何配置，可以直接让卡巴斯基不对 api.deepseek.com 做加密连接扫描。

路径：卡巴斯基主界面 → 设置（齿轮图标）→ 常规设置 → 网络设置 → 加密连接扫描 → 受信任地址（或“管理排除项”）→ 添加，输入 api.deepseek.com。

这是“只在杀软侧改动、DSH 零改动”的方案，适合不希望触碰环境变量的用户。需要注意的是，不同卡巴斯基版本中该入口的名称可能略有差异（“受信任地址”“排除项”“受信任域”），但都位于“网络设置”下的“加密连接扫描”区域。

一个容易踩的坑：如果先停掉卡巴斯基测试，再跑诊断命令看到正常的证书链，不能据此认为卡巴斯基不是中间人。必须在扫描开启的状态下测试，才能看到 issuer 变为卡巴斯基、authorized 为 false 的真实状态。

第三步：处理行为拦截（形态 A）

启发式报毒的逻辑与 TLS 问题完全不同。DSH 的正常工作模式包括启动 shell、读写本地文件、执行 Node/Python 代码、发起外联请求。这套行为组合在启发式引擎看来，与恶意软件的行为特征高度重叠。社区中的判断是：问题出在“权限给得太高”，而不是 DSH 本身含有恶意代码。

卡巴斯基的启发式检测无法仅凭“像不像”来区分开发工具和恶意软件，只能依靠“做了什么”。DSH 恰好做了一连串在行为层面与恶意软件难以区分的事情。

处置方式是在卡巴斯基中为 DSH 添加排除项或受信任进程。

按文件/文件夹排除：设置 → 安全设置 → 排除项和检测到对象时的操作 → 管理排除项 → 添加，浏览选择 DSH 的安装目录或可执行文件，勾选适用的保护组件，保存。

按进程排除（如果卡巴斯基版本支持）：在排除范围中选择“按处理程序”，指定 DSH 的进程路径。这种方式比按文件夹排除更精确，因为它只豁免 DSH 自身的行为，不影响该目录下其他文件的扫描。

添加排除后，卡巴斯基仍会对 DSH 之外的文件和进程保持正常扫描，这是排除项相对于“完全关闭防护”的优势。

验证与两条通用注意事项

验证 TLS 修复：设置完 NODE_USE_SYSTEM_CA 或 NODE_EXTRA_CA_CERTS 后，重启 DSH，再次运行第一步中的 node -e 诊断命令。如果输出 HTTP 200 或类似状态码，说明 TLS 握手已通过。

验证行为排除：在 DSH 中正常执行一次涉及 shell 调用和文件读写的操作，观察卡巴斯基是否再弹窗。

第一条注意事项：NODE_USE_SYSTEM_CA 和 NODE_EXTRA_CA_CERTS 需要 DSH 进程能够读到。如果 DSH 是通过快捷方式、launcher 或 IDE 启动的，确保环境变量在启动它的父进程环境中已生效，或在系统级变量中设置后重启终端/桌面环境。

第二条注意事项：如果上述方案都未能解决 TLS 问题，检查是否有其他中间人软件同时在运行（Clash 透明代理、企业 DLP 等）。多个中间人叠加时，证书链可能被重签两次，仅信任卡巴斯基的根证书不够，需要把链路中每一层中间人的根证书都加入信任，或者逐层排查、逐层排除。
