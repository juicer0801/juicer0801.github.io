4.2 字符问题

文字说：“‘字符串’是个相当简单的概念… 问题出在‘字符’的定义上。”

1. Python 的进化史

  • 在 Python 2 里，str 其实是原始的字节序列（也就是 0和1），而 unicode 才是真正的文本。
  • 在 Python 3 里，纠正了：str （人类懂的），bytes （机器懂的）。

2. 什么是“码点（Code Point）”？

  • 原文：“字符的标识，即码点，是 0~1 114 111 范围内的数（十进制），前加 ‘U+’。”
  • 喵喵喵：码点就是字符的“身份证号”。比如字母 A 的身份证号是 U+0041，欧元符号 € 的身份证号是 U+20AC。在全世界，只要拿着这个号码，谁都知道你说的是哪个字符。

3. 什么是“编码（Encoding）”？

  • 有码点还不够，还要把它存进硬盘、发给别人，得转换成真实的“字节”。
  • 编码，就是一套规则，规定了“把哪个码点变成哪几个字节”。
  • 比如字母 A，在 UTF-8 编码规则下，它只占 1 个字节：\x41。

4. 编码 vs 解码

  • 编码（Encode）：从人类懂的文本（str）变成机器懂的字节（bytes）。把码点变字节。
  • 解码（Decode）：从机器懂的字节（bytes）变回人类懂的文本（str）。把字节变码点。

示例 4-1 代码拆解

补充点 1：什么是 UTF-8？

为什么 é 在 UTF-8 里要占 2 个字节

  • 因为早期的计算机全是英文，只认 ASCII（1 个字节存一个字母）。UTF-8 是聪明的“变长编码”：可以兼容老代码。普通英文只占 1 个字节，只有遇到中文、日文、特殊符号（如汉字通常占 3 个字节，emoji 占 4 个字节）时，才会变长。这就节省了存储空间。

实战

场景 1：Token 长度 ≠ 字符长度 ≠ 字节长度
在大模型（如 ChatGPT、LLaMA）中，文本会被切分成 Token。不同分词的算法底层极度依赖字节。
比如，单词 "café"：

  • 人类看到的长度：4（字符数）
  • len("café".encode('utf-8')) 的长度：5（字节数）
  • 在 GPT-2 的分词器下，它的 Token 长度可能是 2（比如切成了 "caf" 和 "é"）。
  • 计算模型的 Context Window（上下文窗口）时，看的一定是 Token 数量，而不是 len(text) 的字符数。

场景 2：Byte-Level BPE（字节级字节对编码）
现在的稍微好一点的大模型（比如 GPT-4、Llama-2）用的都是 Byte-level BPE 分词器。根本不管你是哪个国家的人，直接把所有的文本编码成 UTF-8 字节序列，然后在字节层面做切分。
为了兼容全人类所有奇奇怪怪的符号（包括 emoji 和生僻字），用纯字符（Unicode）去切分极容易出错（比如出现未知的 OOV 词），而转换成 bytes 之后，任何文本都变成了一串数字，彻底解决了 OOV 问题。

场景 3：处理多语言数据集
假设你在训练一个机器翻译模型，你要限制一个 batch 里句子的最大长度。
如果你用 len(sentence)（按字符数截断），由于中文字符占 3 个字节，英文字母占 1 个字节，会导致底层内存极其不均衡。通常我们会先 encode 成字节，或者利用 Tokenizer 统一处理。

总结：

  1. str 是给人看的（字符串），bytes 是给机器看的（字节）。
  2. .encode() 变成字节（存储/传输），.decode() 变成文本（阅读/处理）。
  3. len(str) 和 len(bytes) 往往不相等。非 ASCII 字符（如中文、表情符号）往往会占多个字节。

实战

场景 1：大模型（LLM）的 Tokenizer 分词机制
现在的顶流大模型（比如 GPT-4、Llama-2）用的都是 BPE（字节对编码） 或 Byte-level BPE。
为什么要用字节级别？因为如果只用字符（Unicode），遇到生僻字或特殊 emoji 就会报 Unknown 错误。如果把所有文字强行转换成 bytes（0-255 的整数），全人类几千种语言、所有乱七八糟的表情包，加起来也就 256 种基础“积木”，模型只要在这 256 个积木里组合就行了。不懂 bytes，你永远学不懂 Transformer 词表底层是怎么构建的。

场景 2：加载和保存模型权重（torch.load）
当你用 PyTorch 保存模型时，model.pth 文件其实就是一个巨大的二进制字节流。读写这些文件时，就避不开 bytes / bytearray 。

场景 3：图像/视频的原始数据读取
用 OpenCV 或 PIL 读图片时，读入的原始数据就是 bytes。如果要做高性能的数据增强，把图片直接转成 numpy.ndarray (dtype 为 uint8)，它其实就是 bytearray 在数学运算领域的变体。在 PyTorch 里，对应的是 torch.uint8 类型的张量。

场景 4：内存视图与网络传输
通过网络（如分布式训练时传参数）发送数据时，bytearray 配合 memoryview（我们在第 49 页学过的零拷贝），可以直接在内存的字节级别进行操作，不需要转化为字符串或复制数据，速度极快。

总结：

  1. 索引取整数（ASCII码），切片取整体（同类型对象）。 这是本节最容易踩的坑。
  2. 大模型之所以能认识所有奇葩字符，就是因为底层把它们全部打碎成了 bytes 来处理。

实战

这次我们不讲基础原理，讲点大模型工程底层的硬核应用。

场景 1：大模型推理引擎的底层通信（vLLM / TensorRT-LLM）
在分布式训练或推理时，GPU 显卡之间、或者多台机器之间需要高速传输张量（Tensor）。这些数据在网络线缆上跑的时候，绝对不是字符串或者 Python 对象，而是纯粹的二进制流（bytes）。
只有把数据打包成连续的 bytes（或者配合之前学的 memoryview 零拷贝），才能获得带宽的最大利用率。你看到的乱码，对计算机来说是最美味的食物。

场景 2：大模型 Tokenizer 的 Byte-Level BPE 机制
之前提过，LLM 是怎么切词的？它把任何人类文字（甚至火星文、emoji）先转成 utf-8 的字节流（bytes）。然后它不按“字符”切，而是按“字节”来切。
比如中文字“深”在 UTF-8 下是三个字节。大模型底层直接把这几个字节看成一个个独立的符号来统计频率。这就是为什么现在的模型不会遇到“未知词汇（OOV）”的原因，因为这世上不存在未知的“字节”。

场景 3：读取超大模型权重文件（.safetensors 或 .pth）
如果你用 open('model.pth', 'rb') 打开一个权重文件，读取出来的全是一堆 b'\x00\xff...' 这样的字节。框架底层会拿着这些 bytes，配合之前讲的 struct 模块（C语言结构体），把它们精确地切分成一个个 float16，最后灌入 GPU 的显存中。

总结：

  1. bytes 索引出整数，切片出 bytes。
  2. 任何模型、任何张量，最后喂给 GPU 的，全是一串按规则排列的 bytes。

索引 vs 切片

“my_bytes[0] 获取的是一个整数，而 my_bytes[:1] 返回的是一个长度为 1 的字节序列。如果你不理解这种行为，只能说明你习惯了 Python 的 str 类型。对 str 类型来说，s[0] == s[:1]。除此之外，对于 Python 中的其他所有序列类型，一个项不能等同于长度为 1 的切片。”

  • 喵喵喵：
    • 对于字符串 s = 'abc'，s[0] 是 'a'，s[:1] 也是 'a'，它们相等。
    • 但对于字节序列 b = b'abc'，b[0] 是整数 97，b[:1] 是字节序列 b'a'，它们不相等
    • 因为序列类型（比如列表、元组、bytes）的切片，规定必须返回同类型对象（哪怕是只切出一个元素），而用索引去取，是获取那个位置的具体值（对 bytes 来说就是 0-255 的整数）。

字节的 4 种“不同”

用 4 种方式显示打印出来的字节序列：

  1. 直接显示 ASCII 字符：32~126 范围内的（空格到 ~），比如 b'caf' 就正常显示。
  2. 用转义字符：比如制表符 \t，换行符 \n，回车 \r，还有反斜杠 \\。
  3. 引号处理：如果里面同时有单引号和双引号，整个序列用单引号 ' 括起来，内部的单引号转义为 \'。
  4. 十六进制转义：其他不在上述范围的字节（比如中文、特殊符号），全部用十六进制的 \x00 形式显示。比如 é 就显示成了 \xc3\xa9。

bytes 能用的方法

作者说：“除了格式化方法… 之外，str 类型的一众方法… 其他方法均受 bytes 和 bytearray 类型的支持。”

  • ruarua：也就是说，endswith（以什么结尾）、replace（替换）、strip（去空格）、upper（转大写）、translate（翻译映射）等，在 bytes 里全都能用，甚至连正则表达式（re 模块）也能直接处理二进制序列。
  • 注意：bytes 没有 format（格式化字符串）和 casefold 等方法，因为那是专门针对人类文本的。
  • 专属方法 fromhex：bytes.fromhex('31 4B CE A9') 可以把一串十六进制字符串直接变成字节对象。这在处理协议数据时有用。

怎么构造 bytes 和 bytearray？

  1. 从文本编码：传一个 str 对象和 encoding 参数（比如上一页的 bytes('café', 'utf-8')）。
  2. 从整数迭代器：传一个装满 0~255 整数的列表/可迭代对象（比如 bytes([1, 2, 3])）。
  3. 从缓冲类对象：传一个 bytes、bytearray、memoryview 或 array.array。这就是缓冲协议（Buffer Protocol），底层会直接复制内存里的字节。

实战

场景 1：内存映射与超大模型加载（mmap）
加载一个 20GB 的大模型（比如 Llama-3）时，内存根本装不下。框架会通过缓冲协议（Buffer Protocol），把文件映射到内存中。读取的时候，底层直接操作字节（bytes），把权重数据（通常是连续的 float16 字节）无缝拷贝到 GPU 显存中，不消耗多余的 CPU 算力去转换。

场景 2：模型权重文件的 .bin 格式
早期的 Hugging Face 模型权重文件全是 .bin（二进制文件）。 open() 读进来，拿到的就是一堆字节。要经过 struct.unpack 或者底层的字节解析，把这些十六进制字符拆解成实际的张量（Tensor）。如果不懂 fromhex 或 \x 转义，连模型文件里面长啥样都看不懂。

场景 3：图像与音频的原始输入
在训练 CV 模型时，读入一张 JPEG 图片，它在内存里一开始就是 bytes 格式。必须用 PIL 或 OpenCV 把它解码成像素矩阵，才能喂给 CNN。

总结：

  1. 索引出整数，切片出字节。
  2. bytes 是只读的，bytearray 是可变的。
  3. bytes 继承了大量 str 的字符串方法，处理二进制文本特别方便。

场景 1：Hugging Face Tokenizer 的乱码报错

  6. utf-16le：Windows 内部和 Java 常用的编码。最少用 2 个字节，所以纯英文的文本用它存储，体积会翻倍。

Emoji 的诞生

“UTF-16 取代了 1996 年发布的 UCS-2… 截至 2021 年，已分配的码点中超过 57% 大于 U+FFFF，包括表情符号 (emoji)。”

  • 摸摸：
    • 早期的 Unicode 标准（UCS-2）认为 6 万多个位置足够全人类用了（最大码点 U+FFFF）。
    • 结果后来发现根本不够，于是发明了 “代理对（surrogate pair）”。在 UTF-16 里，遇到超过 U+FFFF 的超大码点（比如各种花里胡哨的 Emoji 😂、🚀），就用两个 16 位（总共 4 个字节） 拼起来表示。
    • 在处理文本长度时，如果遇到 Emoji，经常会出现莫名其妙的 Bug（比如 len("😂") 可能是 2，也可能是 4，取决于底层编码）。

4.5 处理编码和解码问题

  1. UnicodeEncodeError（编码错误）：
    • 代码思路：想把人类文本 str 变成字节 bytes。
    • 错误：密码本里根本没有要存的字。比如要把一段纯中文存进只认英文字母的 ascii 编码里。
  2. UnicodeDecodeError（解码错误）：
    • 代码思路：想把字节 bytes 翻译成人类文本 str。
    • 错误*：拿错了密码本。比如数据是用 utf-8 写的，非要用 gb2312 去翻译，翻译出来的东西如果是非法字符，直接报错。
  3. SyntaxError（语法错误）：
    • 错误*：这通常发生在写 Python 代码时，文件头部没有声明编码（Python 3 默认 UTF-8，但在某些老旧系统里，或者在代码里直接敲了极其罕见的字符）。

补充

补充点 1：errors 救命参数

遇到 UnicodeDecodeError 且数据无价（比如爬来的网页、读入的日志）时，不能用 try-except 直接跳过。应该用 errors 参数：

  • s.decode('utf-8', errors='ignore')：直接把无法解码的坏字节无视掉。
  • s.decode('utf-8', errors='replace')：把坏字节替换成乱码符号 � (U+FFFD)，至少知道这里缺了东西。

补充点 2：为什么 Windows 老是乱码？

Windows 中文版默认的编码是 GBK（cp936）。你在 Linux 或 Mac 上用 utf-8 写的 Python 脚本，一拿到 Windows 的 CMD 里运行，屏幕上就会飘出 锟斤拷 或 烫烫烫。（hhh）终极解法：在代码开头永远写上 # -*- coding: utf-8 -*-，并且用 utf-8 进行读写。

实战

场景 1：Hugging Face 数据集
在用 Hugging Face 的 datasets 库加载某个开源数据集时，偶尔会遇到 UnicodeDecodeError。这是因为上传这个数据集的人，用的是一个残缺的密码本（比如把带 BOM 头的 utf-8 和 gbk 混着存了）。

场景 2：LLM 训练时遇到 Emoji 暴增
如果在微调大模型（比如用 LoRA 微调 LLaMA-3）时，训练数据里包含大量 Emoji 表情。按照刚才的“代理对”理论，这些表情在底层占用的字节数（和 Token 数）远超普通文字。如果不做长度截断，极其容易导致显存溢出（OOM）。
解法：在数据预处理阶段，强制通过正则表达式过滤掉 Emoji，或者把 max_length 调大，并且使用 Byte-level BPE 的分词器。

场景 3：图像处理中的字节流
在用 OpenCV 读图片时，如果你用 img = cv2.imread('xxx.jpg')，读出来的是像素矩阵（NumPy 数组）。但如果用 open('xxx.jpg', 'rb') 读出来，拿到的是 bytes。如果把这个 bytes 存入数据库（比如 Redis 或 MongoDB）时乱码了，它对应的像素矩阵就会被破坏，图片就彻底废了。

总结：

  1. utf-8 是默认标准。
  2. 看到 UnicodeDecodeError，就说明读数据时密码本不对，加上 encoding='utf-8' 试试。
  3. 不要用非 ASCII 密码本去存人类语言（除中文特殊场景外）。

为什么需要 BOM？（大端 vs 小端）

其实就是计算机界著名的“吃鸡蛋先敲大头还是小头”。

  • 字母 ‘E’ 的码点是十进制 69（十六进制 0x45）。
  • 小端序（Little-endian，Intel CPU 常用）：低位字节写在前面。所以 ‘E’ 存成字节就是 69, 0（0x45, 0x00）。
  • 大端序（Big-endian，网络传输常用）：高位字节写在前面。’E’ 存成字节就是 0, 69（0x00, 0x45）。
  • 如果你不告诉电脑用哪种顺序读，它就会把 El 读成 lE。所以，BOM 应运而生，它对应的不可见字符是 ZERO WIDTH NO-BREAK SPACE (U+FEFF)。在小端序系统里，它被存成了 b'\xff\xfe'。

补充点 1：UTF-8 需不需要 BOM？

不需 文本里说 Unicode 标准允许 BOM，但在 utf-8 编码下，强烈建议不要加 BOM。
但是，万恶的 Windows 记事本（Notepad）在保存 UTF-8 文件时，默认会加一个隐形的 BOM（变成 EF BB BF）。这就导致你在 Linux 上用 Python 读文件时，字典里的第一个 Key 会莫名其妙多出一截，变成 \ufeffkey。这就是很多 AI 工程师抓狂的源头。
解法：如果你遇到这种文件，读取时把编码改成 encoding='utf-8-sig'，-sig 就是专门用来吃（并忽略）BOM 的。

补充点 2：为什么大语言模型的文件全是无 BOM 的 UTF-8？

因为 BOM 对现代计算机来说不仅没用，还会污染数据。如果在训练大模型（比如 LLaMA）时，数据集的每句话前面都带个 BOM 字符，模型会把它当成一个全新的 Token 学进去，白白浪费算力。

默认编码

Python 寻找默认编码的优先级（从高到低）：

  1. 显式指定：如果代码里写了 encoding='xxx'，那它就是老大。
  2. 环境变量：如果没写，Python 会去翻系统环境变量 PYTHONIOENCODING。如果设置了，就用它。

  4. 读写文件时：如果直接 open('file.txt')，底层找的就是 locale.getpreferredencoding()。

locale.getpreferredencoding() 才是决定文件读写是否乱码。

视觉欺骗

一种特殊情况：有些字符，看起来长得一模一样，但存储却不一样。

  • 剖析：
    • 第一种表示法（NFC）：把字母 e 和重音符号 ´ 组合成了一个现成的独立字符 é（码点 U+00E9）。所以长度是 4（c, a, f, é）。
    • 第二种表示法（NFD）：用了两个字符，一个是普通的 e，另一个是“组合重音符号”（码点 U+0301）。它附着在前一个字符上。所以长度是 5（c, a, f, e, ´）。
    • 这就是 Unicode 里的“异体同义（Canonical equivalent）”。人眼觉得一样，但 Python 的底层字符串比较是逐字节/逐码点比的，所以判定为 False。

什么是兼容性归一化？

作者首先解释了 NFKC 和 NFKD 中的 K 代表 Compatibility（兼容性）。

  • 剖析：Unicode 为了兼容以前各种乱七八糟的旧标准（比如一些老式打字机或旧系统的字符集），收录了大量“长得像，或者意思相近，但在计算机底层有不同的码点”的字符。
  • K 系列规范化，就是把这些为了“兼容”而存在的“变体”，强行变成它最基础、最标准的本体。它比 NFC/NFD 强硬得多。

欧姆符号与希腊字母

  • 解读：在底层，欧姆符号 Ω 和希腊大写字母 Ω 的码点不一样NFC 认为它们有物理区别（比如数学公式里，一个是电阻单位，一个是希腊字母）。
  • 作者提到，NFC 不会把微符号变成希腊字母，但 NFKC 会。这就是 K（兼容性）的威力：它不管你的物理意义。

NFKC 的“暴力拆解”

1. 分数

  • 一个漂亮的单字符 ½，被拆分成了三个字符 1、/、2。

2. 上标数字

  • 原本表示“4的平方”的 4²，被 NFKC 强行转换成了普通的数字 42。

补充点 1：NFKC 到底适合用来干什么？

4.7.1 大小写同一化（casefold ）

经常要把所有文本转成小写，免得 “Apple” 和 “apple” 被模型当成两个词。普通人的做法是 .lower()，但我推荐用 .casefold()。

  • 解析：
    • .lower() 只是把 ASCII 字母变成了小写。
    • .casefold() 是为了“无视大小写进行严格比较”而设计的。它不仅把字母变小写，还会按照 Unicode 规范，把那些特殊的字符转成标准的小写形式。
    • 德语的 ß 在 casefold() 下变成了 ss。

补充（为什么一定要用 casefold？）

在 Python 官方文档中，明确指出：如果你是为了进行不区分大小写的比较（比如 if s1.lower() == s2.lower()），请使用 casefold() 替代 lower()。

因为 Unicode 极其庞大，很多字符的小写转换规则极其变态。除了刚才的 ß，还有土耳其语里的 İ、希腊语里的 Σ。如果你用 .lower()，在某些语言环境下会引发极其诡异的 Bug。

4.9.2 字符的数值意义

“unicodedata 模块中有几个函数可以检查 Unicode 字符是不是表示数值… 能确定人类可读的具体数值，而不是码点数。”

Python 里有三个相似、但含义不同的方法：

  1. str.isdecimal()（十进制数）：最严格。只有纯正的十进制数字（0-9，以及全角的０-９）才返回 True。
  2. str.isdigit()（数字）：放宽了一点。除了 isdecimal 里的字符，它还认上标/下标（比如平方的 ²，立方的 ³）。
  3. str.isnumeric()（数值）：最宽容。它包含了 isdigit，还认罗马数字（Ⅳ）、中文的数字（四、一）、甚至分数（½）。
  • 函数 unicodedata.numeric(char)：这个函数直接把字符转成真实的 float 浮点数。比如 numeric('½') 会返回 0.5，numeric('四') 会返回 4.0。
  • 例子 4-22 ：最下面提到了正则表达式 re.compile(r'\d')。注意：在默认情况下，Python 的正则 \d 匹配的是所有 Unicode 数字（等同于 isnumeric），如果你只想匹配 0-9，必须加上 re.ASCII 标志。

什么是“双模式 API”？

作者指出：“Python 标准库中的一些函数能接受 str 或 bytes 为参数，根据其具体类型展现不同的行为。re 和 os 模块中就有这样的函数。”

场景 3：Windows 的长路径限制（260 字符）
在 Windows 上，如果训练模型时缓存路径太深（比如 Hugging Face 的默认缓存路径），结合含有中文字符的用户名，极易触发系统的“路径过长”报错。这背后其实是 Windows API 在处理 str 和底层路径 bytes 转换时的历史遗留问题。

总结：

  1. 正则表达式加 re.ASCII
  2. os 模块支持 bytes 路径
  3. 所有的文件路径、文件名，全部使用纯英文

场景 1：大语言模型（LLM）的 BPE 分词底层
为什么 GPT-4 这种大模型能认识全世界的语言？因为它们底层采用的是 Byte-level BPE（字节级字节对编码）。它根本不在乎你输入的是中文、泰文还是 emoji，它直接用 .encode('utf-8') 把你输入的文本打碎成二进制字节（Bytes），然后在字节层面进行拼接。不懂本章的 str 和 bytes 的相互转换，你根本看不懂 Tokenizer 的源码。

场景 2：数据清洗 Pipeline 的“黄金流水线”
当你在处理一个极其脏的英文数据集（比如从推特爬下来的）时，你的标准处理流程（基于本章知识）应该是：

  1. 用 utf-8-sig 读取文件。
  2. 用 unicodedata.normalize('NFKC', text) 统一全半角和特殊兼容符号。
  3. 用 casefold() 把所有大小写拍平。
  4. 用 re 模块配合 re.ASCII 干掉所有非 ASCII 的乱码或生僻外文符号。
  5. 编码成 bytes，送入 Tokenizer。
    这 5 步走完，你的模型收敛速度绝对比别人的快，且极少报错。

场景 3：多模态模型的图文对齐（CLIP 等）
文本端经过上面的清洗和 Tokenizer 变成了张量，图像端变成了像素矩阵。底层多进程（DataLoader）在进行数据搬运时，文件名、路径、元数据，随时都可能因为操作系统的默认编码（Windows 的 GBK 和 Linux 的 UTF-8）发生冲突。铁律依然是：代码里所有的路径、文件名，绝对、绝对、绝对不要用中文！
