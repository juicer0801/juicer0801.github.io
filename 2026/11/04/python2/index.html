内置序列类型

Python 的内置序列可以按两个维度切分：一是“装引用还是装值”，二是“能不能改”。先看第一个。

容器序列与扁平序列

容器序列：list、tuple、collections.deque。

它们可以混装任意类型的项，也可以嵌套，[1, "hello", True, [3.14, 2.71]] 完全合法。底层存放的是对象的引用（指针）。可以把它们想成快递柜：柜格里放的不是货物本身，而是一张写着“物品 A 在 1 号仓库”的纸条。

扁平序列：str、bytes、array.array。

它们只能存放同一种简单类型的项，你写不出 [1, "hello"] 这样的数组。底层在自己的内存空间里直接存储值本身，像一长条连续的格子，格子里塞满了具体的数值。

图 2-1：两种内存布局

左边：元组 (9.46, 'cat', [2.08, 4.29])

这是典型的容器序列。最上面的方框是一个数组，但里面装的不是实际的值，而是灰色方块——指针。这些指针分别指向内存中真正的对象：一个浮点数、一个字符串，以及一个内部含两个指针的列表。

它足够灵活，但内存是分散的。遍历这个元组时，CPU 要不断跳到不同地址取数据，容易发生缓存不命中（cache miss）。

右边：数组 array('d', [9.46, 2.08, 4.29])

这是扁平序列。它是一个整体对象（对 C 语言数组的 Python 包装），内部是一块连续内存，整整齐齐地放着 9.46、2.08、4.29 三个双精度浮点数（d 代表 double）。

它不够灵活（只能放一种类型），但速度极快：数据连续排列，CPU 读取第一个数据时，会顺带把相邻数据一起拉进高速缓存。

NumPy 的 ndarray 和 PyTorch 的 Tensor 都要求元素类型一致（例如全是 float32），实现上也以连续内存为常态（非连续视图在参与运算前通常要先 contiguous()）。它们本质上是“极其复杂的扁平序列”。DL 里动辄上百万个元素的矩阵乘法，如果数据像左边那样到处乱指，GPU 根本没法高效并行；只有右边这种扁平、连续的内存布局，GPU 才跑得动。

灵活与性能往往是互斥的。 内置 list 追求极致的灵活，而做 AI 数据处理追求的是吞吐量，所以我们会借 numpy 或 torch.tensor 把数据转成底层连续的扁平序列。

扁平序列为什么更紧凑

任何 Python 对象在内存里都不是光秃秃的值，它有一个包含元数据的标头（header）。书里拆了一个浮点数在 C 层面的结构，三个部分各占 8 字节，共 24 字节：

  1. ob_refcnt（引用计数）：记录有多少个引用指向它。计数归零，对象立刻被回收。
  2. ob_type（类型指针）：告诉 Python“我是个浮点数”。
  3. ob_fval（值）：真正存放 9.46 的地方。

假设有一个含 3 个浮点数的元组 (9.46, 2.08, 4.29)，内存里就有 3 个这样的标头，外加元组自身的标头和 3 个指针。但换成数组 array('d', [9.46, 2.08, 4.29])，整体只有一个标头，后面直接连续塞进 3 个纯 double。

按 64 位 CPython 算，三个 PyFloatObject 光是“引用计数 + 类型指针”就多出 3 × 16 = 48 字节，元组还要再用 3 个指针（24 字节）指向它们；而数组那边，同样的三个数只占 24 字节。数据量一大，差距就拉开了。

Tensor 能存一百万张图片的像素，正是因为它不为每个像素造一个 Python 对象，而是在底层申请一块连续的大内存，只存数值。

按可变性分类

可变性说的是对象创建之后，里面的项能不能被替换、增删。

  1. 可变序列：list、bytearray、array.array、collections.deque。可以 append、pop，也可以直接替换某个元素。DL 里构建动态的 batch 列表，用的一定是 list。
  2. 不可变序列：tuple、str、bytes。一旦创建，里面的东西不能变。DL 里模型的输入维度常写成元组，比如 (batch_size, 3, 224, 224)。

图 2-2 把类之间的关系画细了。看左边的三个框和右边的 MutableSequence。

Sequence（不可变序列的模板）

它只要求实现两个抽象方法：__getitem__ 和 __len__。只要有了这两个，__contains__、__iter__、__reversed__、index、count 这些混入方法（mixin）就都能从 ABC 里直接继承。这也解释了为什么一个只实现了 __getitem__ 和 __len__ 的自定义类，看起来就已经“像个序列”——当然，它并不会因此自动获得虚拟子类的身份，issubclass 那一关仍然要靠注册。

MutableSequence（可变序列的模板）

它的箭头指向 Sequence，继承了后者的全部能力，并新增三个抽象方法：__setitem__（赋值）、__delitem__（删除）、insert（插入）。如果你自定义的类继承了 MutableSequence，在 Sequence 要求的两个方法之外，只再实现这三个，那么 append、extend、pop、remove、reverse 这些方法 Python 会自动帮你生成。因为 append 的本质就是在末尾 insert，框架把这类基础操作都搭好了。

副作用与排版提示

作者有一句原话：

“仅仅为了得到副作用，就用列表推导式重复执行代码段。如果你不打算使用生成的列表，那就不要使用列表推导式。”

比如想打印一堆数据，或者把数据写进文件。写 [print(x) for x in data] 就很蠢：推导式是用来生成并返回新列表的，拿它干别的事，不仅可读性差，还会白白生成一个全是 None 的废列表。要副作用，老老实实用 for 循环。

排版上有两条：

  • 括号 ()、[]、{} 内部换行，不需要加反斜杠 \。
  • PEP 8 建议多行时在最后一个元素后面留一个尾随逗号，比如 [1, 2, 3,]。这样以后加新元素，不用回头改上一行，Git diff 也只显示新增的一行。

列表推导式的局部作用域

书里提到：Python 3 中的列表推导式有局部作用域。

在 Python 2 时代，写 [x for x in range(5)]，循环结束后变量 x 会覆盖外部同名的 x，也就是变量泄漏。Python 3 改掉了这一点，推导式有了自己的作用域。

内部的循环变量不会污染外部变量，这是一个很大的进步，堵掉了一类莫名其妙的 Bug。

补充一个实现细节：Python 3.12 之前，列表推导式会被编译成一个隐式函数，所以有独立作用域；3.12 起（PEP 709）推导式被内联进外层代码，省掉了函数调用的开销，但作用域隔离的行为没有变。

海象运算符 :=

既然 Python 3 把变量锁在了推导式内部，那如果外部确实需要用到推导式里算出来的最后一个值呢？

Python 3.8 引入了海象运算符 :=（:= 看起来像海象的两只眼睛和獠牙）。

last := ord(c) 的意思是：算一下 ord(c)，顺便把这个值赋给外层的 last。于是 last 在推导式外可以访问，值是 67（'C' 的 ASCII 码）。

但循环变量 c 依然被锁在推导式内部，外面调用直接 NameError。这个特性了解一下即可，日常写代码尽量别在推导式里搞得这么绕。

生成器表达式

书里的原话：

“虽然列表推导式也可以生成元组…… 但是生成器表达式占用的内存更少，因为生成器表达式使用迭代器协议逐个产出项，而不是构建整个列表提供给其他构造函数。”

  • 列表推导式 []：把所有结果全部算出来，在内存里占一块很大的空间，然后交给你。
  • 生成器表达式 ()：只记下“怎么算”的规则，不提前算。你要一个，它算一个、给一个。内存占用极小。
  • 语法差别：把方括号 [] 换成圆括号 () 即可。

PyTorch 的 DataLoader 底层就是这套思路：不把数据集一次性读进内存，而是一批一批地产出。

array 与生成器

注意这里括号不能省。array() 构造器要两个参数：类型代码（'I' 表示无符号整数）和数据源（这里是生成器）。既然有两个参数，生成器外面的圆括号就必须留着。

示例 2-6：不构建列表的笛卡儿积

“与示例 2-4 不同，这一次 6 种 T 恤衫组成的列表不在内存中构建…… 如果两个各有 1000 项的列表，则使用生成器表达式一次性计算笛卡儿积可以节省大量内存，因为不用先构建一个包含 100 万项的列表提供给 for 循环。”

算一笔账：

  • 用列表推导式 [(c, s) for c in colors for s in sizes]：内存里立刻建起一栋装着 100 万个元组的“大楼”，RAM 可能直接飙红。
  • 用生成器 ((c, s) for c in colors for s in sizes)：内存里只有一台“豆浆机”。按一下（循环一次），磨出一杯（产出一个元组），喝完再磨下一杯。内存占用几乎为 0。

这正是写 Dataset 时必须懂的原理：不要一次性加载所有数据，用生成器，或者用 DataLoader 分批加载。

喵一嘴：注意这里用的是 () 而不是 []。在 for 循环驱动下，它按顺序把 6 种组合吐出来。f'{c} {s}' 是 f-string，很适合给训练日志打标签。

AI补充：生成器只能遍历一次

生成器是“一次性”的：遍历完就空了，再 list() 它只会得到空列表。要复用，就重新创建，或者用 itertools.tee 复制（但 tee 会在内部缓存，省不了多少内存）。

另外，如果最终要把所有元素都放进内存，列表推导式通常比生成器表达式快，因为生成器每产出一项都有额外开销。生成器的价值在于“不占内存”和“可以表示无限流”，不在于快。

元组：不只是不可变列表

从 2.4 节开始进入新章节。作者一上来就打破一个刻板印象：

“有些 Python 入门教程把元组称为‘不可变列表’，然而这没有完全概括元组的特点。除了可以作为不可变列表使用之外，还可用作没有字段名称的记录。”

喵一嘴：

  • 误区：很多新手觉得元组就是“不能改的 list”，这太小看它了。
  • 真相：元组在 Python 里扮演两个截然不同的角色。
    1. 记录（record）：比如 (x, y) 坐标，比如 DL 里的 (batch_size, channel, height, width)。每一项有特定含义，位置不能乱换。
    2. 不可变列表：把一堆数据丢进元组，仅仅是为了防止别人改。

书里接下来主要讲“元组当记录”这一用法。

元组作记录

“用元组存放记录，元组中的一项对应一个字段的数据，项的位置决定数据的意义。”

喵一嘴：为什么是“位置决定意义”？想想 PyTorch 里的 for batch_data, labels in dataloader:：batch_data 永远在位置 0，labels 永远在位置 1，反了模型就废了。

两个好处：

可哈希性

书里有一句话，是写复杂 Python 脚本时一定会遇到的报错源头：

“存放可变项的元组可能导致 bug。读到 3.4.1 节，你会发现，只有值永不可变的对象才是可哈希的。不可哈希的元组不能作为字典的键，也不能作为集合的元素。”

什么是哈希：字典和集合的底层是哈希表，放进去的键必须有一个稳定的“身份证号”（哈希值）。

避坑指南：

  • 元组里的元素全部不可变（(1, 'abc', 3.14)），这个元组可哈希，能当字典的键。
  • 元组里包含列表（(1, [2, 3])），列表随时可变（哈希值会变），这个元组就不可哈希。
  • 写 my_dict = {(1, [2, 3]): 'value'}，Python 会直接抛 TypeError: unhashable type: 'list'。

AI补充：可哈希性的几个细节

  • “不可变才可哈希”是经验法则，不是语言强制。用户自定义的类默认按 id() 哈希，哪怕它的属性可变，也照样能当字典键——只是两个内容相同的实例会被当成两个不同的键。
  • 反过来，只要你在类里定义了 __eq__ 却没定义 __hash__，Python 3 会把 __hash__ 置为 None，这个类的实例立刻变成不可哈希。这是很常见的坑。
  • 元组的哈希是对元素的哈希做组合，所以 hash((1, (2, 3))) 没问题，hash((1, [2])) 直接报错。
  • 需要“不可变的集合”当键时，用 frozenset。

元组为什么更快

这部分引用了 Python 核心开发者 Raymond Hettinger 在 Stack Overflow 上的回答。三个原因：

编译时优化（常量折叠）

“Python 编译器求解元组字面量时，经过一次操作即可生成元组常量的字节码。”

写 t = (1, 2, 3) 时，Python 在把源码编译成字节码的阶段，就已经把 (1, 2, 3) 当成一个整体常量打包好了。用的时候一条 LOAD_CONST 直接拿出来。而 l = [1, 2, 3] 必须在运行时先建空列表，再逐个把 1、2、3 塞进去，多了一步。

内存分配：列表的“预支”机制

“给定一个元组，分配的内存空间正好够用。而 list 实例的内存空间要富余一些…… 一旦超出当前分配的空间，Python 就需要重新分配引用数组来腾出空间，而这会导致 CPU 缓存效率较低。”

  • 元组长度固定，创建时量体裁衣，要 3 个元素就只给 3 个。
  • 列表长度可变。为了让你以后 append 时快一点，每次扩容都会多要一点内存。比如只存了 10 个元素，它可能已经向系统要了能装 16 个槽位的空间。塞爆之后，它要重新找一块更大的空地，把数据全搬过去，这个搬运过程很耗 CPU。
  • 缓存：元组的指针数组紧凑，能更好地利用缓存行；列表常留着闲置空位，浪费缓存行，命中率下降。

拷贝的“偷懒”哲学

“tuple(t) 直接返回 t 的引用，不涉及复制。相比之下，list(t) 创建 t 的副本。”

因为元组不可变，t2 = tuple(t1) 时 Python 会想：反正你不能改，何必复制？直接让 t2 指向 t1 就行，速度零损耗。而 l2 = list(l1) 哪怕 l1 有一亿个元素，也得老老实实复制一遍，内存瞬间翻倍。

AI补充：关于“元组更快”的边界

这段性能对比很容易被读成“元组永远比列表快”，实际不是。

  • 差距在纳秒级。只有在百万次量级的创建/销毁循环里，才值得为这点差距改数据结构。日常代码里，选元组的首要理由应该是语义（定长记录、可哈希），性能只是顺带的好处。
  • 常量折叠只对字面量生效。(1, 2, 3) 是编译期常量；(a, b, c) 依然要在运行时 BUILD_TUPLE，只是比建列表少一次扩容。
  • tuple(t) is t 是 CPython 的实现细节，不是语言保证。别写依赖它的逻辑，PyPy 或未来的 CPython 都可能变。
  • 缓存友好的说法要打折。元组里的元素（比如 float 对象）仍然散落在堆上，元组只是让指针数组更紧凑；真正吃性能的矩阵运算应该交给 ndarray / Tensor，靠 tuple 省不出数量级的差距。
  • 想量化就用 timeit，别信“感觉更快”。

  • 前面我们知道 _ 匹配单个元素。这里引入了 *_（星号加下划线），表示“匹配任意数量的项，而且我连变量名都懒得取，直接全扔掉”。

2.7.1 为什么切片要“排除最后一项”？（左闭右开原则）

文字原话：“切片和区间排除最后一项是一种 Python 风格约定”。

解释：
当你写 s[1:3] 的时候，取出来的是索引 1 和 2，不包含索引 3。这叫“左闭右开”。

为什么要这么设计？

  1. 算长度太方便了：当只有最后一项被排除时，你只要做一次减法就能算出切片的长度。stop - start。比如 s[1:3]，长度就是 3 - 1 = 2。如果包含最后一项，每次算长度都得在心里加个 1（3 - 1 + 1 = 3），极其反人类。
  2. 完美切分：如果你想把一个列表分成两半，写成 s[:x] 和 s[x:]。因为左闭右开，这两块拼起来正好是整个列表，中间绝不重叠，也绝无遗漏。如果是左闭右闭，那得写成 s[:x] 和 s[x+1:]，一旦 x 变了，代码很容易写出 Bug。
  • 大佬背书：下面文字提到了计算机科学家 Edsger W. Dijkstra（Dijkstra 最短路径算法的那个大佬）。他在几十年前专门写了一篇备忘录，论证了为什么从 0 开始计数，并且采用“左闭右开”是最优雅的。如果你对数学感兴趣可以读读，记住包头不包尾

2.7.3 多维切片

“[] 运算符还可以接受多个索引或切片，以逗号分隔。负责处理 [] 运算符的特殊方法 __getitem__ 和 __setitem__ 把接收到的 a[i, j] 中的索引当作元组。”

1. 语法背后的原理

在 Python 里，写 a[i, j]，Python 在底层会把它变成一个元组 (i, j)，然后调用 a.__getitem__((i, j))。

  • 重点：元组是作为一个整体参数传进去的。 这就是为什么 NumPy 和 PyTorch 可以支持 tensor[0, 1] 这种操作。它们内部的 C 代码接收到了这个元组，然后去解析各个维度。

2. 内置类型的限制

文字说：“除了 memoryview 之外，Python 内置的序列类型都是一维的，因此只支持一个索引或切片，不支持索引或切片元组。”

  • 如果你对普通的 Python 列表写 my_list[0, 1]，程序会报错 TypeError: list indices must be integers or slices, not tuple。只有 NumPy 数组和 PyTorch 张量才重写了 __getitem__ 来支持多维操作。

3. 二维切片演示

比如在 NumPy 里，a[m:n, k:l] 意思是：在第一个维度（比如行）取 m 到 n，在第二个维度（比如列）取 k 到 l。

  • 这就对应了 tensor[0:2, :] 取前两个样本的所有特征。

  • 如果没找到（比如 a 是不可变序列，如 tuple、str，或者是你自己随便写的类）：Python 就只能退而求其次，去调用 __add__（也就是普通的 +）。这就等于执行了 a = a + b。它会创建一个全新的对象，然后让变量 a 指向这个新对象。

2. 一句话总结

  • 可变序列（List）：+= 是就地修改，效率极高，不占新内存。
  • 不可变序列（Tuple）：+= 是重新建对象，原来的元组直接丢弃。
  • （文字最后也提到，*= 和 __imul__ 的关系，也是完全一样的逻辑。）

list.sort vs sorted

1. list.sort() 方法（就地排序）

  • 特征：只属于列表（List），而且它是“就地修改”的。
  • 返回值：返回 None。
  • 绝对不要写 l = l.sort()！,如果你这么写了，l 直接变成 None，原列表虽然被排好序了，但你把这个变量给弄丢了。
  • 作者的用意：为什么返回 None？这是 Python 的 API 约定。为了明确提醒你：“我是在原地改的，我没给你新东西”。
  • 缺点：这种设计有个坏处——不能级联调用（流式接口）。比如字符串 s.strip().lower()，因为 strip() 返回了新字符串，所以能接着调 lower()。但如果你 my_list.sort().append(1)，直接报错（因为 sort 返回 None，None 没有 append 方法）。

2. 内置函数 sorted()（建新副本）

  • 特征：接受任何可迭代对象（列表、元组、字符串、甚至生成器）。
  • 返回值：不管传什么进去，它永远返回一个全新的排好序的列表。原数据不变。

参数（reverse 和 key）

这两个参数 list.sort() 和 sorted() 都有。

1. reverse

  • 大白话：reverse=True 就是降序排列（从大到小），默认是 False（从小到大）。

2. key

文字解释：一个只接受一个参数的函数，应用到每一项上，作为排序依据。

  • 翻译：直接排序，Python 只能按元素本身比大小（数字比大小，字母比 ASCII 码）。但如果给 key 传了一个函数，Python 会先把所有元素送进这个函数计算出一个“分数”，然后按这个“分数”来排序。
  • 书上的例子：
    • key=str.lower：忽略大小写排序。
    • key=len：按字符串长度排序（短的在前，长的在后）。
  • 提示：除了排序，内置的 min()、max()，以及标准库里的 itertools.groupby()、heapq.nlargest() 等，全都有 key 参数。学会一个，到处通用。

  • 解读：通过底层的二进制拷贝，一千万个数据复制到了 floats2 里。

array 和 Tensor啥关系？

既然 array 这么好，为什么深度学习不用它，而要用 numpy.array 或 torch.Tensor？

1. 为什么不用原生 array？
因为原生 array 虽然省内存，但它不支持数学运算！不能写 array_a * 2 或者 array_a + array_b。它只是用来“存”数据的，不是用来“算”数据的。

2. 张量（Tensor）的底层逻辑
numpy.ndarray 和 torch.Tensor 底层就是升级版的 array。它们同样在内存里开辟一块连续的区域，存放纯 C 语言的数字（比如 float32）。
正因为底层是这样连续的纯数值，GPU 才能像切豆腐一样，把这块内存分给几千个核心同时去算（SIMD 并行计算）。

3. 模型的保存（model.state_dict()）
当你在 PyTorch 里保存模型时，底层其实就是在做类似 tofile() 的操作。把模型的权重（一堆巨大的连续浮点数）直接以二进制形式倒进 .pt 或 .pth 文件里。这也是为什么预训练模型动辄几个 G，但加载速度通常还能接受的原因。

总结：

  1. 能用 set 解决的高频查找，就不用 list。
  2. 纯数值、大容量，用 array 或 Tensor，不用 list。
  3. 读写二进制文件（wb / rb）比文本文件快一万倍，且不丢失精度。

2.10.2 memoryview

原话：“经常使用数组的人不知道 memoryview，可谓遗憾终生。”

1. 什么是 memoryview？

  • 打个比方：假设你有一块巨大的金砖（数据），你想在它上面雕花。如果你用普通方法，得先把金砖融化，复制一块新的，再雕。而 memoryview 就像是在金砖上盖了一块透明的玻璃板。你透过玻璃板去读写底层的金砖，不需要复制数据。
  • 作者引用了 NumPy 之父 Travis Oliphant 的话：“memoryview 在数据结构之间共享内存，而不是事先复制。这对大型数据集来说非常重要。”

2. cast() 方法

文字说：“memoryview.cast 方法使用的表示法与 array 类似… 改变读写多字节单元的方式，无须移动位。返回另一个 memoryview 对象，而且始终共享内存。”

  • 解读：cast 就是“变形”。底层的数据没有变，位置没变，仅仅是“看它的角度”变了。

  • 注释 ❸ 深度解析 cast('B', [2, 3])：
    • 'B'：依然按单字节读取。
    • [2, 3]：把这个一维的内存块，在逻辑上切分成 2 行 3 列。

PyTorch 的 view 和 reshape 从哪来？

x.view(2, 3)
它底层用的就是类似 memoryview.cast 的机制（所以它叫 view，中文叫“视图”）。
没有复制这 6 个数字，只是在底层修改了张量的元数据（metadata），让GPU以另一个视角看待这个数据

这也是为什么 view() 有时候会报错：因为如果原来的张量在内存里不是连续排列的（比如经过了转置 tensor.T），就没法直接“切块”看，必须先用 .contiguous() 把内存重新排列连续，然后才能 view()。

总结：

  1. array 不能直接排序，用 sorted 包一下。
  2. memoryview 是 Python 高阶数据处理的门槛，实现了“零拷贝”。
  3. cast 可以改变数据的维度和形状，底层数据不变。这正是 numpy.reshape 和 torch.view 的前身。

  • 注释 ❸ 核心解读：m1、m2、m3 这三个视图（View），底层共享的是同一块内存。不管你把它看成 1x6、2x3 还是 3x2，底层的那 6 个字节（0到5）在物理内存里的位置没动。cast 只是改变了读取数据时的“步长”和“维度信息”。

这和 Tensor 到底有什么关系？

  1. 张量的 .view() 与底层：
    PyTorch 的 tensor.view() 就是上面的 memoryview.cast()。它没有复制数据，只是改变了解释这段内存的形状。
  2. 数据类型转换的陷阱：
    在 PyTorch 里，如果写 x = x.to(torch.int8) 或者做位操作（Bitwise operation），底层其实就是在做例子里“多字节转单字节”的操作。如果对浮点数用位操作，就会得到完全不可理解的“乱码”（就像 -2 变成了 254, 255）。
  3. 大模型（LLM）的量化（Quantization）：
    大模型能在手机上，就是跑开发人员使用了量化技术。比如把原本占 2 个字节的 float16，硬生生压缩成只占 1 个字节的 int8。这种极端的压缩和变形操作，底层完全建立在对内存字节的精准操控上，也就是今天的 memoryview 的终极延伸。

总结：

  1. 用 cast() 转换类型，只要总字节数能对上（比如 10 字节变成 10 个单字节），就不会报错，但读出来的值会完全不一样（因为底层二进制没变，只是解释方式变了）。
  2. memoryview 让我们拥有了像 C 语言指针一样直接操作内存的能力。

为什么列表在头部操作很慢？

第三板块：2.10.4 双端队列 deque

为了解决上面的问题，Python 标准库提供了 collections.deque（double-ended queue，双端队列）。

1. 为什么 deque快

  • 打比方：list 就像是一列火车，你要在车头加一节车厢，整列火车都要往后推，极其困难。而 deque 像是一串手拉手的人。要在最前面加人，直接在前面挂一个人就行了，后面的人根本不用动。
  • 底层原理是“双向链表”或“分块数组”。在两端添加或删除元素的时间复杂度是 （瞬间完成），而 list 是 。

2. deque 的特性

  • maxlen 参数：文字提到“需要保留‘最后几项’…有界的 deque 对象填满之后，从一端添加新项，将从另一端丢弃”。
  • 线程安全：文字提到它是“线程安全”的。也就是说，多个线程同时从 deque 的两端塞数据和拿数据，不会导致数据错乱。

deque实践

场景 1：滑动窗口（Sliding Window）
在时间序列预测（比如预测股票、或者语音识别）里，需要每次提取过去 10 秒的数据。用 deque(maxlen=10) ，新数据进来，旧数据自动滚出。

场景 2：记录最近的 Loss
在训练大型模型时，想在控制台打印最近 100 个 batch 的平均 Loss 来看看收敛情况。用 deque(maxlen=100)，你永远只会存着最新的 100 个。

场景 3：多线程数据读取
在用 PyTorch 的 DataLoader 时，后台会有多个进程（Worker）不断地把图片从硬盘读出来，放进一个共享的队列里，主线程负责从队列里取数据训练。这个底层队列的机制，就极度依赖于线程安全的双端队列。

总结：

  1. NumPy 的向量化计算和二进制存取。
  2. 尾部操作多用 list，头部操作或需要固定长度队列，选 deque。

  • 喵喵喵：前面说了，list 是一块连续的内存。而 deque 底层是由一块块固定大小的内存块链接起来的（双向链表结构）。在头部和尾部加减元素，只需改变指针指向即可，速度是 极快。但如果你想在中间插队，它需要遍历寻找那个位置，所以很慢。

2. 为什么它是“线程安全”的？

  • 作者说：“append 和 popleft 是原子操作（Atomic Operation），因此你可以放心地在多线程应用中把 deque 作为先进先出队列使用，无须加锁。”
  • 解读：在 Python 的多线程编程里，如果用普通的 list 让多个线程同时去 pop 和 append，很容易因为 CPU 切换时间片导致数据错乱（比如两个线程同时拿到了同一个数据）。为了不出错，通常需要加“锁”（Lock）。
  • 但 deque 的 append 和 popleft 是原子操作。这意味着在 Python 底层（C 语言层面），这步操作是不可分割的，绝对不会被打断。所以你用它做线程间的数据队列，不需要加锁，安全且高效。

deque 的能与不能

  1. 都有的：s.pop()（弹出最后一个）、s.remove(e)（移除指定元素）、s.reverse()（翻转）、s.__setitem__()（通过索引赋值）。
  2. 只有 list 有，deque 没有的：
    • s.sort()：deque 没有排序方法！ 它的底层是链表结构，链表做随机访问和排序极其困难。如果你想排序，得先转成 list：sorted(my_deque)。
    • 切片：作者解释里写了，“deque 不支持切片”。因为没有连续的内存，所以不能写 my_deque[1:3] 这种操作。
  3. 只有 deque 有的：s.extendleft(iter) 和 s.rotate(n)。

脚注：提到如果要删除列表中的某一项，deque 甚至没有直接提供 del 方法，得用 pop(p) 替代，但速度很慢。

Python 的“队列三剑客”

1. queue 模块（多线程安全队列）

  • 原文解析：“类都有界——构造函数提供 maxsize 参数，设为大于 0 的值… 利用这种行为可以限制活动线程的数量。”
  • 白话：在 Python 里，因为“全局解释器锁（GIL）”的存在，多线程其实并没有真正利用多核 CPU。但即便如此，如果你要写多线程爬虫、或者开多个线程读文件，必然涉及线程间的数据交换。queue.Queue 就是最安全的通道。它自带“锁”，往里面塞数据，不用怕两个线程抢同一个数据。
  • 经典队列类型：
    • Queue：先进先出（FIFO），排队买票。
    • LifoQueue：后进先出（LIFO），其实就是栈，吃薯片。
    • PriorityQueue：优先队列，VIP 客户先办业务（底层其实就是用堆 heapq 实现的）。

2. multiprocessing 模块（多进程安全队列）

  • 解读：multiprocessing.Queue 是用于多进程通信的。多进程不共享内存，数据完全隔离，所以要通信必须把数据序列化后通过网络或管道传过去

3. asyncio 模块（异步队列）

  • 讲师解读：这是 Python 近几年最火的“协程”框架。在写异步网络爬虫、或者搭建像 FastAPI 这样的高并发 Web 服务时，asyncio.Queue 用来管理异步任务的排队。

CPU 读取硬盘数据、做预处理（数据增强）然后喂给 GPU 的过程。

用 multiprocessing 开了一堆子进程，然后用队列（Queue）做桥梁。

场景：PyTorch 的 DataLoader 工作原理

  1. 主进程（负责训练）向队列里扔一个任务：“嘿，帮我读第 1 到 32 张图片”。
  2. 后台的 Worker（子进程）拿到任务，吭哧吭哧读盘，用 deque 或其他结构做数据增强。
  3. Worker 处理完，把这 32 张图片转成 Tensor，塞进 Queue 里。
  4. 主进程直接从 Queue 里拿现成的 Tensor 喂给 GPU。
  • 如果不用 Queue，主进程和子进程直接硬碰硬传数据，不仅慢，而且数据非常容易发生冲突或丢失。因为 Queue 内置了锁机制和阻塞机制（队列满了工人就等，队列空了 GPU 就等），整个流程才能像齿轮一样精密咬合。

总结：

  1. 两头增删用 deque，并发通信找 Queue。
  2. deque 不支持切片和排序，因为它不是连续内存。
  3. 随着对大模型（LLM）的研究，数据流（Data Streaming）处理越来越多，理解这三种队列（线程、进程、异步）十分必要。

这段科普了我们在第 16 页学过的“容器序列”和“扁平序列”的官方定义。

  • 官方文档里的“坑”：

为什么 key 是非常聪明的设计？

文字提到，Python 2 里面的排序是用 cmp(a, b)（比较函数），而 Python 3 淘汰了它，全面换成了 key。为什么？

  • 核心原因：计算次数。
    • 旧方法 cmp：排序时，每比较两个元素，就要调用一次函数。如果有 100 万个元素，排序算法可能要进行 2000 万次比较，就要调用 2000 万次 cmp。
    • 新方法 key：每个元素只调用一次 key 函数！它把每个元素先算出一个“比较权重”，然后再用底层极快的 C 语言去比较这些权重。
  • 这就是典型的“空间换时间”。用 key 函数相当于给每个元素贴上了“身价标签”，之后全看标签说话，原数据不动。这也是为什么你以后在 PyTorch 里给张量排序，通常要用 torch.argsort() 并配合 key 逻辑（按某一列的值排）。
