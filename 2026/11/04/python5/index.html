引言

“数据类就像小孩子。作为一个起点很好，但若要让它们像成熟的对象那样参与整个系统的工作，它们就必须承担一定责任。” —— Martin Fowler 和 Kent Beck

  • 这两位是软件工程界的神级大佬（《重构》的作者）。这句话其实在警告我们：不要把“数据”和“行为”完全割裂。
  • 在很多早期的 Java 教程里，喜欢让人写纯纯的“数据类”（只有一堆属性，加上一大堆 getter/setter 方法），然后所有的业务逻辑全写在其他的 Service 类里。业内认为这叫“贫血模型”，是代码异味。但在 Python 里，很多时候我们确实只需要一个用来装数据的盒子，只要用得恰当，它依然是极好的工具。

数据类

本章要介绍的是 Python 中用来构建这种“简单类”（主要用来当容器装字段，几乎没有额外功能）的三种快捷方式。它们被统称为数据类（data class）模式。

  1. collections.namedtuple：最古老（Python 2.6 就有）。
  2. typing.NamedTuple：带类型提示的“进阶版”（Python 3.5 引入）。
  3. @dataclasses.dataclass：功能最强大、最现代（Python 3.7 引入）。

作者说，这三种方式相比于自己手写繁琐的 class，“增加了大量选项，可实现更复杂的功能”。

为什么叫“数据类”？

注 1：引用自《重构：改善既有代码的设计》… 接下来将讨论为什么数据类模式也是一种代码异味，它的出现可能意味着面向对象设计欠佳。

  • 在纯粹的 OOP（面向对象编程）中，一个类应该既有数据，又有操作这些数据的方法（高内聚）。如果写了一堆只有变量、没有方法的类，代码的维护性可能会变差。但请注意，在 Python 的数据科学和 AI 领域，这条规并非绝对的，因为我们经常需要纯粹的数据载体。

补充

补充点：为什么我们爱用“数据类”取代普通的字典（Dict）？

config = {"lr": 0.01, "batch_size": 32}
字典的缺点：

  1. 写错键名不会报错：config["lrr"] 运行到这一行才会报 KeyError。如果是数据类，IDE（代码编辑器）直接给你标红。
  2. 没有类型提示：不知道 batch_size 传个字符串 "32" 进去会不会把模型搞崩。
  3. 字典是动态的，占用内存大，运行慢。数据类底层是普通类的实例，速度快得多。

collections.namedtuple

  • 剖析：
    • 本质：namedtuple 其实是个工厂函数。传给它的字符串 'lat lon'，它会用 split() 切开，然后在底层动态地生成一个继承自 tuple 的类。

  • 传一个列表，里面每个元素是 (字段名, 类型) 的元组。这比直接写字符串麻烦，但编辑器有了提示。

实战

场景 1：Hugging Face 的 TrainingArguments
微调大模型时，通常需要设置几十个参数（learning_rate, batch_size, weight_decay, logging_steps…）。Hugging Face 就是用 @dataclass 来定义 TrainingArguments 的。只需要调用 TrainingArguments(...)，传错参数名，IDE 会直接标红，运行起来也可以直接把整个配置通过 asdict() 存成 JSON 文件。

查 Hugging Face 的底层源码，会发现 ModelOutput 其实就是一个 dataclass。它不仅支持像元组一样解包 loss, logits = outputs，还能让你在生成任务中，动态地往输出里塞入 past_key_values 这种超长缓存。这就归功于 dataclass 的可变性和灵活性。

场景 3：管理数据增强策略
做图像数据增强时，定义了一个 TransformConfig。如果用 dataclass(frozen=True)，在初始化后，增强概率就无法被修改了。

总结：

  1. typing.NamedTuple 本质上是元组，不可变，性能高，适合做数据样本（Batch）或简单输出。
  2. @dataclass 本质上是普通类，灵活，可定制，默认可变（如果不写 frozen=True），适合做复杂的配置对象或状态管理器。
  3. 配置用 dataclass，传递数据轻量载体用 NamedTuple。

表格收尾（ API 大赏）

  • 获取默认值：NamedTuple 用 x._field_defaults；dataclass 用 [f.default for f in fields(x)]。
  • 获取字段类型：NamedTuple 和 dataclass 都有 x.__annotations__。
  • 更改后创建新实例：
    • NamedTuple 用 x._replace(...)。
    • dataclass 用 dataclasses.replace(x, ...)。

6 大区别

1. 可变实例

  • 提炼：NamedTuple 是 tuple 的子类，不可变。dataclass 默认可变。但如果你写了 @dataclass(frozen=True)，它就变成了不可变，效果类似 NamedTuple。

2. Class 语句句法

  • NamedTuple（指 typing 版本）和 dataclass 都支持 class 语法，看起来都很正统。老式的 collections.namedtuple 只能写一行工厂函数，不行。

3. 构造字典（转 JSON 必备）

  • 两者都能把对象瞬间变成一个纯字典。NamedTuple 用 _asdict()；dataclass 用 dataclasses.asdict()。
  • 实战把模型配置保存成 config.json。

4. 获取字段名称和默认值

  • NamedTuple 靠的是内置属性 _fields（元组格式）。
  • dataclass 靠的是 dataclasses.fields() 函数，返回的更强大，连默认值、字段类型全都有。

5. 获取字段类型

  • “不推荐直接读取 __annotations__ 属性。推荐使用 inspect.get_annotations(MyClass)（Python 3.10 新增）或 typing.get_type_hints()。”
  • 很多时候你会看到网上教人直接用 x.__annotations__ 去拿类型，但这在继承关系复杂时很容易出 Bug。官方推荐用 get_type_hints。

6. 更改之后创建新实例

  • NamedTuple 用 _replace，dataclass 用 replace。
  • 白话：因为不能直接改对象（或者不想改原对象），所以要拿一个旧对象当模板，改几个参数生成一个新对象。_replace(lat=100) 就是复制一份，顺便把 lat 改成 100。

补充（_replace 与 replace 的底层逻辑差异）

  • NamedTuple._replace 底层非常快，因为它只需要构建一个新的元组。
  • dataclasses.replace 底层要稍微复杂一点，因为它得重新调用一遍 __init__ 或者 __post_init__ 方法。如果你在 __post_init__ 里写了复杂的校验逻辑，replace 也会触发它。

补充

补充点 1：字段名的“雷区”

在定义 namedtuple 的时候，字段名不能乱起：

  • 不能是 Python 的关键字（比如 class, def）。
  • 绝对不能以下划线 _ 开头。因为以 _ 开头的名字（如 _fields）是 namedtuple 内部保护的方法。如果起名叫 _name，会直接冲突报错。

补充点 2：单元素元组的逗号

namedtuple 也是元组，所以如果它只有一个字段，在实例化或者创建它的时候，如果漏了逗号，也会引发bug。比如 Point = namedtuple('Point', ['x'])。

5.6 @dataclass 详解 QAQ

给出 @dataclass 装饰器的完整签名：
@dataclass(*, init=True, repr=True, eq=True, order=False, unsafe_hash=False, frozen=False)

  • 翻译：
    • init=True：自动生成 __init__ 方法（如果设为 False，就得自己写）。
    • repr=True：生成漂亮的打印字符串。
    • eq=True：重写 == 比较，按值比较，而不是按内存地址比较。
    • order=False：默认不生成比较大小的方法。如果设为 True，就能用 <、> 去比较两个对象。
    • frozen=False：默认是可变的。如果设为 True，就相当于锁死，变成类似 NamedTuple 的不可变状态（但底层机制不同）。
    • unsafe_hash：复杂哈希运算，高级功能，先不管。

哈希的诅咒与恩赐（unsafe_hash 规则）

  1. 默认情况：frozen=False（可变）时，@dataclass 会把 __hash__ 设置为 None。这意味着你的对象不可哈希，不能当字典的键（Key），也不能放进集合（Set）。
  2. 自动生成：如果同时写了 @dataclass(frozen=True)（不可变）且 eq=True，它会自动生成一个安全的 __hash__ 方法。对象就可以当 Key 了。
  3. 强制生成：可以写 @dataclass(unsafe_hash=True) 强制生成哈希。但作者不建议这么做（因为它可变，一旦改了值，哈希值就变了，字典就找不到它了）。

    • 正确：a: int; b: int = 10

“@dataclass 生成的 __init__ 方法只做一件事：把传入的参数及其默认值赋值给实例属性。可是，有时候我们想做一些额外的初始化操作，比如验证，如果存在这个方法，则 @dataclass 将在生成的 __init__ 方法最后调用 __post_init__ 方法。”

  • 剖析：假设你写了一个配置类，其中有个 learning_rate。你不希望用户传个负数进来。但是 @dataclass 自动生成的 __init__ 只管赋值，根本不会校验。
  • 但是自己手写又会买椟还珠，得不偿失
  • 解法：__post_init__。它在底层的执行顺序是：
    1. 执行自动生成的 __init__（把参数绑成 self.xxx）。
    2. 紧接着，自动执行你在类里面写的 __post_init__(self)。

什么是“代码异味（Code Smell）”？

“代码异味是一种迹象，通常表明系统存在深层问题… 异味能被‘闻到’。内容较长的方法就有异味…”

  • “代码异味”不是语法错误，代码能跑，也没有 Bug。但是很抽象，比如：一个函数写了 500 行；变量名叫 a, b, c；或者——只有一个纯数据类，所有操作它的逻辑全写在了别的类里。

为什么数据类是“坏味道”？

“所谓数据类是指，它们拥有一些字段，以及用于访问（读写）这些字段的函数，除此之外一无长物。这样的类只是一种不会说话的数据容器，它们一定被其他类过分烦琐地操控着。”

  • 喵喵喵：
    • 在经典的面向对象编程（OOP）里，这叫“贫血模型”。数据（属性）和行为（方法）被硬生生剥离了。
    • 举个反例：你定义了一个 Point 类，只有 x 和 y 属性。然后你在另一个类里写了一个 calculate_distance(point) 的函数。
    • 因为 Point 自己应该知道怎么算距离，应该写成 point.calculate_distance()。你把它的方法抽走，放到别的类里去操作，这就导致了强耦合，代码难维护。

然而真的无用吗？

  • 情境差异：
    • 传统软件（如银行系统）：账户余额不仅是个数字，它还包含“转账”、“冻结”、“计息”等行为。纯数据类就不好。
    • AI 框架与数据科学：我们需要进行矩阵运算、需要把参数序列化成 JSON、需要给模型喂纯张量（Tensor）。这时候，数据和行为必须解耦！一个用来存配置的 Config 类，它就该老老实实当个容器，越纯粹越好。我们不需要“会自己计算梯度的配置”。

补充（如何消除异味？）

Fowler 给出的解药是：“遇到数据类，请问自己一个问题：这个类需要什么行为？ 然后，开始重构，加入需要的行为。”

  • 在 Python 里的具体做法：
    • 如果你非要用 @dataclass 存数据，但有些逻辑确实跟数据强相关。利用我们上一节学的 __post_init__！ 或者直接在类里面写普通的方法。
    • 比如我们的 Resource 类，你可以给它加个方法 def is_valid(self): return self.identifier != ''。这就给它注入了灵魂，它就不再是纯粹的“不会说话的数据容器”了。

5.7.1 把数据类用作“脚手架”（什么时候可以用？）

作者给出了数据类被广泛接受，且不会变成“坏味道”的四种绝佳场景：

  1. 刚开启新项目时：需要快速写个模块跑通流程，先用数据类快速搭个架子，把数据装起来，以后再把行为慢慢加进去。
  2. 类应当完全独立：这个类不依赖其他类的方法，它就只是个单纯的“信息包裹”。
