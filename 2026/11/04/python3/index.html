  • 这句话并不是夸张。在 Python 底层，类属性（self.name）、模块的命名空间、函数的参数（**kwargs），甚至调用的所有内置函数（存储在 __builtins__.__dict__ 里），全都是用字典来维护的

    • 在加载 Hugging Face 的预训练模型时，读入的 config.json 就是一个典型的字典。

3.1 本章新增内容（字典的“进化史”）

  1. 合并字典的神器（| 和 |=）：
    • “包括自 Python 3.9 开始受 dict 支持的 | 和 |= 运算符。”
    • 解读：以前合并两个字典超级麻烦，要么用 update() 破坏原字典，要么写 {**dict1, **dict2}。现在有了 |，你可以直接写 merged = dict1 | dict2，就像数学里的求并集一样。
  2. dict 彻底取代了 OrderedDict：
    • “自 Python 3.6 起，dict 也能保留键的插入顺序。”
    • 解读：以前 Python 的字典是乱序的，要想记住插入顺序，必须用 collections.OrderedDict。但从 3.6 开始，官方原生字典在底层直接加上了顺序保证。所以在现代 AI 代码中，基本可以直接用原生 dict，不用特意去引 OrderedDict 了。
  3. 视图对象（View Objects）：
    • “讲解 dict.keys、dict.items 和 dict.values 返回的视图对象。”
    • 写 model.state_dict().keys() 时，拿到的不是一个大列表，而是一个“视图”。它的好处是极省内存，它就像一个窗户，你看着字典里的数据，但并没有把数据复制一份出来。
  4. 底层优化：
    • “节省了内存，还能保留键的插入顺序。”
    • 说明 Python 核心开发者为了更省内存，把哈希表的底层数据结构重写了，挤掉了以前浪费的空隙。

2. 字典字面量中的 **（合并字典）

  • 其实这就是我们在第 29 页学的，用 ** 把一个字典拆开，塞进另一个新字典里。

3. 键冲突的法则

  • 原字典里的 x=1 和后面拆包进来的 x=4。最终结果是 4。
  • 规定喵：在字典拆包合并时，如果遇到重复的键，后面的值会覆盖前面的值。

3.2.3 使用 | 合并映射（Python 3.9）

在 Python 3.9 之前，合并字典要么用 .update()（破坏原字典），要么用 {**d1, **d2}。现在有了 |，一切都结束了。

1. | 运算符（并集）

  • 解读：| 和 {**d1, **d2} 的效果一模一样。遇到相同的键 a 和 b，d2 的值覆盖了 d1 的值，并且生成了一个全新的字典。d1 和 d2 本身没变。

2. |= 运算符（就地更新）

  • 解读：这就像我们之前学的 +=。|= 是原地修改。它把 d2 的内容合并进 d1 里，d1 的变量地址没变，只是内容增加了。如果你要频繁把一个庞大的字典合并进主字典，用 |= 更省内存（不用每次新建对象）。

3.3 使用模式匹配处理映射

我们用 match/case 匹配了序列（列表/元组）。现在，我们要用它来匹配映射（字典）。

1. 映射模式

  • 原文：“映射的模式看似 dict 字面量，其实能够匹配 collections.abc.Mapping 的任何具体子类或虚拟子类。”
  • 白话：在 case 里面写 {'type': 'book'}，它代表的不是“这个字典必须和我长得一模一样”。它的真实含义是：“不管这个大字典里装了多少乱七八糟的键，只要它包含了 type 这个键，并且值是 'book'，就算匹配成功”。
  • 核心差异：匹配序列（列表）要求长度严格一致，但匹配映射（字典）是“子集匹配”！ 在 case 里没写的键，都会被自动忽略。

2. 它的应用场景

  • 文字特意提到：JSON API、MongoDB、PostgreSQL 等。
  • DL 实战：调用 OpenAI 的 API，返回的数据是一个巨大的嵌套字典。里面有 choices，有 usage，有 id。只需要提取 role 和 content。这时候用 match/case 匹配字典结构。

3.4 映射类型的标准 API

1. 为什么要用抽象基类？

文字说：“collections.abc 模块中的抽象基类 Mapping 和 MutableMapping… 主要作用是确立映射对象的标准接口，并在需要广义映射对象时作为 isinstance 测试标准。”

  • 翻译：在 Python 里，字典（dict）是“事实标准”。但除了 dict，还有很多其他类型的字典（比如第三方库自己写的、或者后面的 defaultdict）。
  • 如果你想写一个通用函数，判断“你传进来的这个对象，到底是不是一个字典（或者像字典）”，千万不要写 isinstance(x, dict)，因为这会把其他长得像字典的类排除在外。
  • 正确写法：isinstance(x, abc.Mapping)。只要这个类实现了字典该有的方法，它就算过关。这就是前面一直强调的“鸭子类型”。

核心 UML 继承图

3.4.1 “可哈希”指什么？

这是全书最核心的底层概念之一。

什么是可哈希（Hashable）？

满足两个条件：

  1. 生命周期内哈希值不变：底层有 __hash__() 方法。
  2. 可与其他对象比较：底层有 __eq__() 方法（判断两对象是否相等）。

铁律：只有可哈希的对象才能作为字典（dict）的键（Key）和集合（set）的元素。

为什么会有这条规则？

哈希表（字典的底层）是怎么找东西的？
当 key 存进字典时，字典会先算一下它的哈希值（一个数字），然后根据这个数字把它塞进特定的内存格子里。等你下次来找的时候，字典再算一遍哈希值，直接去那个格子拿东西。

  • 如果这个 key 在里面被修改了，它的哈希值就会变。当你再拿着原来的特征去找它时，就找不到了。

所以，谁能当键？谁不能？

  • 能：数字（int、float）、字符串（str）、元组（tuple，但前提是元组里的每一个元素也都必须可哈希）。
  • 不能：列表（list）、字典（dict）、集合（set）。因为它们是可变对象，随时可能被“原地修改”。
  • PyTorch 的张量（Tensor）默认是不可哈希的！ 因为张量是可变对象（你可以写 tensor[0] = 5）。如果你试图写 my_dict[torch.tensor([1,2])] = 'value'，直接报 TypeError: unhashable type: 'Tensor'。

底部脚注 2（强迫症作者的吐槽）

  • 作者说：我喜欢用“哈希码”这个词，而不是“哈希值”。有些不懂装懂的人会说“哈希值容易被混淆”，其实只要知道它是用来做键的就行了。这段是翻译和作者的碎碎念，略过即可。

  3. 只要你想把一个对象放进 set 里，或者当 dict 的键，它必须是不可变的（元组、字符串、数字）。

“可哈希”的判定

这段代码极其直观地演示了上一页的理论：元组（tuple）是可哈希的，但前提是里面的“所有元素”都必须可哈希。

1. 成功案例（tt）

  • 讲师解读：tt 是个元组，里面装了两个数字和一个内部元组 (30, 40)。因为数字和元组都是不可变的，所以整体 tt 是可哈希的。

2. 失败案例（tl）—— 经典的报错

  • 解读：tl 也是个元组，但里面装了一个列表 [30, 40]。因为列表是可以随时修改的（append，pop 等），一旦修改，它的哈希值就会变，字典的底层索引就会崩溃。因此，Python 直接拒绝为包含列表的元组计算哈希值。
  • 这就解释了为什么我们在第一章造的扑克牌 Card 类如果要做字典的键，里面绝对不能存列表。

3. 补救案例（tf）

  • 解读：如果你非要在元组里套一个“集合”，那就必须用 frozenset（冻结的集合）。它跟普通集合的区别就是不可变，所以它是可哈希的。

4. 关于自定义类的底层规定

右侧文字提到：“用户定义的类型默认是可哈希的… 如果自己实现了 __eq__()，就必须实现 __hash__()。”

  • 翻译：在 Python 里，如果你写了一个类，默认你比较两个对象是否相等，比的是内存地址（id()）。如果你的两个对象内容完全一样，但地址不同，它们是不相等的。
  • 如果你重写了 __eq__（改成判断内容是否一样），那么你必须重写 __hash__（让内容相同的对象拥有相同的哈希值）。否则，字典就找不到东西了。

实战：为什么 Tensor 不能当字典的键？

  • Tensor 是可变的。你可以写 tensor_key[0] = 5。
  • 怎么解决？ 如果你真的想用 Tensor 的特征值作为键（比如做缓存），你需要把它变成不可变的形式，比如转成元组：tuple(tensor.tolist())，或者直接转成字符串 str(tensor)。

三剑客

1. d.get(k, [default])

  • 解读：直接写 d[k] 如果字典里没有这个键，程序直接报错崩溃（KeyError）。但如果你用 d.get(k)，找不到就返回 None；如果你写 d.get(k, 0)，找不到就返回 0。
  • DL 实战：在 NLP 里查词表，遇到不认识的词（OOV问题），千万别用 d[word]，一定要用 d.get(word, unk_id)，把生词统一定向到 <UNK> 标记。

  • 解读：获取字典的键、值、键值对。表格里特别写了，它们返回的是视图对象。意思是它们只占极小内存，不复制数据，改动原字典，视图立刻跟着变。

  • 解读：弹出并删除指定的键。常用于你需要“消费”掉某个配置项，用完就删，防止重复使用。

现代语法与派生类专属

  • 解读：这就是我们上一节刚学过的合并字典的运算符（Python 3.9 引入）。

  • 解读：用来倒序遍历字典。因为从 Python 3.6 开始字典自带顺序，所以现在可以直接 reversed(d) 了。

3. OrderedDict （看中间列）

  • d.move_to_end(k, [last])：这是一个特殊的方法，只有 OrderedDict（有序字典）才有。它能把某个键移动到字典的最前面或最后面。

update 的鸭子类型

“d.update(m) 处理第一个参数 m 的方式是‘鸭子类型’的典型应用：先检查 m 有没有 keys 方法，如果有，则假定 m 是映射；否则，退而求其次，假定 m 是键值对形式。”

  • 解析：当你想给字典更新数据时，写 my_dict.update(other)。
    • 如果 other 是一个字典（因为它有 keys() 方法），Python 就按字典的方式遍历它。
    • 如果 other 不是字典，但它是长得像 [('a', 1), ('b', 2)] 这样的可迭代对象，Python 也不会报错，而是默认里面装的是一个个“键值对元组”，照样给你更新进去。
  • 这种“我不在乎你是什么类型，只在乎你能干什么（有没有 keys 方法）”，就是 Python鸭子类型。

总结

  1. 能不用 d[k] 取值，就尽量用 d.get(k)，防止程序崩溃。

3.5.1 defaultdict

虽然 setdefault 很好了，但每次都要打那十几个字母，还要传个 [] 进去，太麻烦了。

看这页的核心文字：“实例化 defaultdict 对象时提供一个可调用对象，当 __getitem__ 遇到不存在的键时，调用那个可调用对象生成一个默认值。”

  • 翻译：你建字典的时候，告诉它：“如果我找了一个不存在的键，你别报错，你帮我造一个默认值填进去再给我。”
  • 比比拉布
    假设你写了 dd = defaultdict(list)，然后访问 dd['new-key']：
    1. 调用 list() 创建一个新列表 []。
    2. 把这个 [] 插入到字典的 'new-key' 键上。
    3. 返回这个 [] 的引用给你用。
  • default_factory：这就是你在创建 defaultdict 时传进去的那个函数（比如 list、int、set）。它被偷偷存成了这个字典的属性。

递归

页面最上方的一段话：

“递归：__missing__ 方法的最后一行 self[str(key)] 将调用 __getitem__ 方法，转而又调用 __missing__ 方法。”

  • 深度剖析：
    这句话描述了一个容易写出来的 Bug。假设你为了把所有的键都转成字符串，在自定义的 __missing__ 里写了 self[str(key)]。
    结果执行逻辑变成了这样：
    1. 你查 d[1]，没找到，触发 __missing__(1)。
    2. 在 __missing__ 里，你写了 self['1']，这又触发了 __getitem__('1')。
    3. 假设字典里连 '1' 也没有，Python 发现键缺失，又一次触发 __missing__('1')。
    4. 死循环了，程序直接卡死报错 RecursionError。

解决——__contains__

为了避免查错，文字里说：“出于对行为一致性的考虑，也需要 __contains__ 方法… 我们没有按照常规的 key in self 检查键，因为 str(key) in self 将递归调用 __contains__ 方法。”

  • 翻译：在自定义字典时，千万别在内部用 key in self，这会引发莫名其妙的连锁反应。正确的做法是用 self.keys() 去查（如 key in self.keys()），这样最安全，而且 Python 3 的 keys() 视图极快。

警告

“用户自己定义的类，如果继承标准库中的映射，在实现 __getitem__、get 或 __contains__ 方法时不一定要回落到 __missing__ 方法…”

  • 解读：很多人的直觉是：字典找不到键 -> 自动调用 __missing__。然而事实并非如此
  • 只有 d[k] 这种通过中括号取值的语法，才可能会触发 __missing__。而 d.get(k) 和 k in d 会不会触发，完全取决于你继承的是谁，以及你怎么写代码。

3.5.3 标准库的“分裂”

这部分展示了 Python 官方标准库里，不同的“字典族”面对缺失键时，行为完全不一样（这其实是历史遗留问题）。

作者分了四种情况，我们直接当表格看：

继承的父类 实现情况 触发 __missing__ 的方法 讲师避坑评价
dict 子类 仅实现 __missing__ 只有 d[k] d.get(k) 不会触发。这符合我们的直觉。
UserDict 子类 仅实现 __missing__ d[k] 和 d.get(k) 因为 UserDict 的 get 底层是用 d[k] 实现的，所以“拔出萝卜带出泥”。
abc.Mapping 子类 (精简版) 自己实现 __getitem__，但不调 __missing__ 永远不触发 就算你写了 __missing__，它也是个摆设，根本不生效。
abc.Mapping 子类 (完整版) 自己实现 __getitem__，且主动调用 __missing__ d[k]、d.get(k)、k in d 都会触发 全自动触发。但这要求你自己手写极其复杂的底层逻辑。
  • 总结：
    如果只是想用默认值，用 defaultdict 就行了！千万别自己去继承 dict 手写 __missing__！
    除非你是在给开源框架写底层组件，否则自己瞎继承，很容易因为不同父类的底层实现差异，搞出一堆无法复现的 Bug。

实战

场景 1：Hugging Face 的 PretrainedConfig
config = AutoConfig.from_pretrained(...)，然后写 config.hidden_size。其实它底层就是一个特殊的字典映射。如果你以后要自己重写底层的 Config 逻辑，去拦截用户输入的错误参数名（找不到就抛异常，或者给个默认值），你必定会用到 __missing__ 或 __getattr__。

场景 2：不要自己造轮子

  • 要默认值 -> 用 defaultdict
  • 要安全取值不报错 -> 用 d.get(k, default)
  • 要在原字典上修改 -> 用 d.setdefault(k, default)

小结：

  1. 在 __missing__ 内部，不要用 self[key]，容易死循环（递归）。
  2. 标准库中不同字典子类，对 __missing__ 的调用规则完全不统一。
  3. 能用 defaultdict 解决的，绝不自定义类。
