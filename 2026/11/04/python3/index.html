3.2.3 使用 | 合并映射（Python 3.9）

在 Python 3.9 之前，合并字典要么用 .update()（破坏原字典），要么用 {**d1, **d2}。现在有了 |，一切都结束了。

1. | 运算符（并集）

  • 解读：| 和 {**d1, **d2} 的效果一模一样。遇到相同的键 a 和 b，d2 的值覆盖了 d1 的值，并且生成了一个全新的字典。d1 和 d2 本身没变。

2. |= 运算符（就地更新）

  • 解读：这就像我们之前学的 +=。|= 是原地修改。它把 d2 的内容合并进 d1 里，d1 的变量地址没变，只是内容增加了。如果你要频繁把一个庞大的字典合并进主字典，用 |= 更省内存（不用每次新建对象）。

3.3 使用模式匹配处理映射

我们用 match/case 匹配了序列（列表/元组）。现在，我们要用它来匹配映射（字典）。

1. 映射模式

  • 原文：“映射的模式看似 dict 字面量，其实能够匹配 collections.abc.Mapping 的任何具体子类或虚拟子类。”
  • 白话：在 case 里面写 {'type': 'book'}，它代表的不是“这个字典必须和我长得一模一样”。它的真实含义是：“不管这个大字典里装了多少乱七八糟的键，只要它包含了 type 这个键，并且值是 'book'，就算匹配成功”。

2. 它的应用场景

  • 文字特意提到：JSON API、MongoDB、PostgreSQL 等。
  • DL 实战：调用 OpenAI 的 API，返回的数据是一个巨大的嵌套字典。里面有 choices，有 usage，有 id。只需要提取 role 和 content。这时候用 match/case 匹配字典结构。

3.4.1 “可哈希”指什么？

这是全书最核心的底层概念之一。

什么是可哈希（Hashable）？

满足两个条件：

  1. 生命周期内哈希值不变：底层有 __hash__() 方法。
  2. 可与其他对象比较：底层有 __eq__() 方法（判断两对象是否相等）。

铁律：只有可哈希的对象才能作为字典（dict）的键（Key）和集合（set）的元素。

为什么会有这条规则？

哈希表（字典的底层）是怎么找东西的？
当 key 存进字典时，字典会先算一下它的哈希值（一个数字），然后根据这个数字把它塞进特定的内存格子里。等你下次来找的时候，字典再算一遍哈希值，直接去那个格子拿东西。

  • 如果这个 key 在里面被修改了，它的哈希值就会变。当你再拿着原来的特征去找它时，就找不到了。

所以，谁能当键？谁不能？

  • 能：数字（int、float）、字符串（str）、元组（tuple，但前提是元组里的每一个元素也都必须可哈希）。
  • 不能：列表（list）、字典（dict）、集合（set）。因为它们是可变对象，随时可能被“原地修改”。
  • PyTorch 的张量（Tensor）默认是不可哈希的！ 因为张量是可变对象（你可以写 tensor[0] = 5）。如果你试图写 my_dict[torch.tensor([1,2])] = 'value'，直接报 TypeError: unhashable type: 'Tensor'。

    1. 你查 d[1]，没找到，触发 __missing__(1)。
    2. 在 __missing__ 里，你写了 self['1']，这又触发了 __getitem__('1')。
    3. 假设字典里连 '1' 也没有，Python 发现键缺失，又一次触发 __missing__('1')。

  • 只有 d[k] 这种通过中括号取值的语法，才可能会触发 __missing__。而 d.get(k) 和 k in d 会不会触发，完全取决于你继承的是谁，以及你怎么写代码。

3.6.1 collections.OrderedDict（有序字典）

“自 Python 3.6 起，内置的 dict 也保留键的顺序。使用 OrderedDict 最主要的原因是编写与早期 Python 版本兼容的代码。”

  • 讲解读：既然现在的普通 dict 已经能保持插入顺序了，那 OrderedDict 难道就废了吗？并没有！ 它比普通 dict 还是要有优势的：

1. 改变插入顺序：move_to_end(k)

  • 普通字典一旦插入，顺序就定死了。但 OrderedDict 可以把某个键移动到最末尾（或者最前面）。
  • 比如在处理特征或者做缓存时，可以把刚刚用过的数据移到末尾。

2. popitem(last=True/False)

  • 普通字典只能按 LIFO（后进先出）弹出一个键值对。
  • OrderedDict 可以设置 last=False，变成 FIFO（先进先出），从头部弹出最老的数据。

3. 应用：LRU 缓存

  • LRU（Least Recently Used，最近最少使用） 是计算机里经典的缓存淘汰算法。
  • 靠 OrderedDict。访问一个数据，用 move_to_end 把它移到末尾；当缓存满了，用 popitem(last=False) 把最前面的（最久没用的）踢掉。貌似PyTorch 的数据加载器底层就有类似思想）。

为什么不能继承 dict？

文字解释：“内置的 dict 在实现上走了一些捷径… 如果继承 dict，那就不得不覆盖一些方法。”

补充点 1：注 8 —— 实例属性的“键共享字典 (Key-Sharing Dictionary)”

  • 文字说：“因为实例的 __dict__ 属性中存储的键是共享的，依附在各个实例上。”
  • 喵喵喵：在 Python 里，你创建一个类的 10000 个实例（比如 10000 个 Cat 对象），每个实例都有自己的 __dict__ 来存属性（self.name, self.age 等）。如果每个实例都存一份完整的 {'name': ..., 'age': ...} 键名，内存就炸了喵。
  • CPython 3.3 以后，让这 10000 个实例共享同一份键名列表，每个实例内部只存一个极小的数组来对应具体的值。这样能极大节省内存。

补充点 2：注 9 —— __slots__

  • 文字提到：“除非另有 __slots__ 属性”（第 11.11 节会详细讲）。
  • 假设要创建几百万个对象，且这些对象只有少数几个固定属性，用普通的类会极慢且耗内存（因为每个对象都要建一个庞大的 __dict__）。如果你在类里写 __slots__ = ('name', 'age')，Python 直接剥夺了该类的实例创建字典的能力，改用一个固定大小的数组来存属性。

ML/DL 实战

在深度学习框架里，字典的底层的极致优化和 __slots__ 简直无处不在：

场景 1：计算图节点的内存优化（__slots__ 的绝佳应用）
在 PyTorch 或 TensorFlow 底层构建“计算图（Computational Graph）”时，一条前向传播可能会产生几百万个“节点”对象。
每一个节点可能只包含：(操作类型, 输入张量, 输出张量, 反向传播函数)。
如果每个节点都带一个庞大的 __dict__ 字典，那显存直接爆了。所以底层框架源码里，这些核心节点类几乎全都用了 __slots__ 。

场景 2：KV Cache（大模型推理加速）
在跑大语言模型（如 LLaMA、ChatGPT）时，有一个吃显存的东西叫 KV Cache（键值缓存）。为了解决长文本的生成速度，模型会把过去算过的注意力矩阵存起来，避免重复计算。
这里的“键（Key）”和“值（Value）”在底层物理内存的分布，完全依赖于现代硬件极致的紧凑内存分配策略。

场景 3：字典的紧凑性在数据处理中的体现
在处理自然语言（NLP）数据时，会经常用 vocab = {'word': id}。几万个词的字典，因为有“紧凑内存布局”（这块数组一分为二，一半放索引，一半放实际数据），查找速度依然是瞬时的，且占用空间极小。

总结：

  1. 视图不能手搓，只能由字典生成，且随着原字典动态变化。
  2. dict 在 3.6+ 版本里重构了内存布局，既保持了插入顺序，又省下了 20% 到 25% 的内存。

PEP 412 键共享字典

这段文字解释了一个内存优化技术：Key-Sharing Dictionary（键共享字典）。

  • 翻译：在 Python 3.3 以前，创建 10000 个对象，内存里就有 10000 个属性字典（__dict__），每个字典都要存一遍键名（比如 'name'、'age'）
  • 现在的优化：类的所有实例共享同一个键的哈希表，每个实例内部只保留一个极小的指针数组来存具体的值。
  • 这个底层优化（PEP 412）直接让面向对象程序的内存使用量减少了 10%~20%。

3.11 集合的实现与性能

“set 和 frozenset 类型都使用哈希表实现。”

  • 特征：
    1. 元素必须可哈希（不可变）。
    2. 成员测试极高效率：无论有 10 个还是 1000 万个元素，if x in my_set 都是瞬间完成的（）。
    3. 内存占用大：这是哈希表的通病。为了减少“哈希冲突”（两个元素抢同一个位置），哈希表必须预留大量的空闲槽位。

彩蛋（注 10：编译期优化）

常量折叠（Constant Folding）。

“只有求解一个集合字面量时才有加速效果… 从 dis 模块导入 dis 函数，反汇编 set 字面量… dis(set([1])) 和 dis({1}) 的字节码。”

  • 解密：
    • 如果你写 my_set = set([1, 2, 3])，Python 运行到这行时，要先建列表 [1,2,3]，再传给 set() 函数去转换。这很慢。
    • 如果你写 my_set = {1, 2, 3}，Python 解释器在编译成字节码（代码还没开始跑）的时候，就直接在内存里把这三个元素组装成一个 frozenset 常量了,程序运行时，直接拿出来用。
    • 注 10 里说的 dis，就是用来看 Python 代码执行了哪些 C 语言级别的指令的。

这段文字解释了集合底层的“扩容与重排”机制。

  • 核心内容：“元素的顺序取决于插入顺序… 如果两个元素具有相同的哈希码，则顺序取决于哪个元素先被添加到集合中。”、“在集合中添加元素后，现有元素的顺序可能会发生变化。”

  • 为什么顺序会变？：
    因为集合底层是基于哈希表的。当集合越来越满（比如填充了三分之二），Python 为了保持极高的查询速度，会把底层的数组扩容，并把所有元素重新“搬家”（重新哈希并分配位置）。
    这就导致了在用 for 循环遍历一个集合的时候，绝对、绝对不能在循环体里往集合里 add 或 remove 元素。 否则一旦触发了扩容，元素的相对顺序全变，Python 会抛出 RuntimeError: Set changed size during iteration。

集合不仅可以算，还可以比较。这在数学上叫“集合论”，在 Python 里，就是比谁包含谁。

1. 子集与真子集

  • s <= z（s.issubset(z)）：判断 s 是不是 z 的子集。意思是，s 里面的东西，z 全都有。哪怕 s 和 z 完全一样，也返回 True。
  • s < z（真子集）：s 是 z 的子集，且 s 不等于 z（z 里至少多出几个元素）。

2. 超集与真超集

  • s >= z（s.issuperset(z)）：判断 s 是不是 z 的超集。意思是，s 包含了 z 里的所有东西。

3. 互斥与成员判断

  • s.isdisjoint(z)：判断 s 和 z 是不是不相交。如果交集为空，返回 True。
    • 注意：这个只能调方法，没有运算符表示。而且它的判定速度快（一旦发现一个交集元素就立刻返回 False）。
  • e in s：看 e 这个元素在不在集合里。

  • 解读：两个字典的 keys() 视图直接求交集，瞬间找出了共有的键。注意：运算结果返回的是一个全新的 set 对象（普通集合），而不是视图了。

2. 视图与普通集合的混合运算

  • 解读：不需要把 d1.keys() 转换成集合，它直接就能和普通集合 s 进行交、并、差运算。这省去了大量繁琐的转换代码。

限制

“仅当 dict 中的所有值均可哈希时，dict_items 视图才可当作集合使用。倘若 dict 中有不可哈希的值，对 dict_items 视图做集合运算将抛出 TypeError。”

  • 剖析：
    • d.keys() 永远安全，因为字典的键必须是可哈希的。
    • 但是 d.items() 不一样！ 虽然键是可哈希的，但值不一定。
    • 假设你有一个字典：d = {'a': [1, 2], 'b': [3, 4]}（值是列表）。
    • 如果写 d.items() & {'a', 'b'}，Python 会直接报错，因为 items() 包含的元组 ('a', [1, 2]) 里面的列表是不可哈希的，不能放进集合里。
  • 在对 dict_items 做集合操作前，一定要确保你的字典里没有列表、字典等可变对象作为值。

3.13 本章小结精读

  1. 现代语法：字典字面量更强大了，支持 ** 拆包、match/case 模式匹配、推导式。
  2. 除了原生 dict，collections 模块下还有：
    • defaultdict（带默认值）
    • ChainMap（多级查找）
    • Counter（计数器，词频统计神器）
    • OrderedDict（虽然原生 dict 已有序，但它的 == 比较会严格考虑顺序，且保留 move_to_end 方法）
    • UserDict（写自定义字典的绝佳基类）
  3. 两大方法：setdefault（更新可变值）和 update（批量合并）。
  4. 魔法：__missing__ 钩子，自定义找不到键时的行为。

补充

视图的“动态性” 和 “运算结果的静态性”

  • 前面讲过，d.keys() 是一个动态视图。如果往 d 里加了新键，这个视图马上就能看到。
  • 但是，一旦你执行了 d1.keys() & d2.keys() 这种运算，结果是一个静态的 set。你之后再修改 d1，刚刚算出来的那个 set 是不会跟着变的。这一点在做缓存或判断时要小心。
