在 Python 里，只要你实现了 __getitem__ 这个特殊方法，Python 解释器就会自动地免费送你一大堆强大的功能。

这叫协议（Protocol）或者鸭子类型（Duck Typing）——“只要它走起来像鸭子，叫起来像鸭子，那它就是鸭子”。（经典名言hhh）

1. 自动支持“切片”（Slicing）

我只写了 __getitem__（获取单个元素），但当我写 deck[1:3]（切片）时，代码居然没报错，直接返回了牌！

底层原理：
当我对对象使用切片语法时，Python 会自动调用 __getitem__。这时的参数不再是整数 0, 1, 2，而是一个 slice 对象（比如 slice(1, 3, None)）。
因为你在 FrenchDeck 的 __getitem__ 里写的是 return self._cards[position]，你把 slice 对象直接传给了底层的列表 self._cards。列表天生支持切片，所以我的扑克牌类也就白嫖了切片功能。

那个 deck[12::13] 是什么意思？
基础复习：[start:stop:step]。
起点是 12（第一张 A，黑桃 A），步长是 13。13张牌是一组花色，所以跳 13 张拿一张，刚好把 4 张 A 全抽出来了。

2. 自动支持“循环遍历”（Iteration）

我没有定义 __iter__ 方法，凭什么能直接用 for 循环？
底层原理：
当 Python 遇到 for x in my_object 时，它第一反应是找对象的 __iter__ 方法。找不到怎么办？
Python 解释器会退而求其次：它发现我有 __getitem__，于是它就会像入机一样，从索引 0 开始，一直调用 deck[0], deck[1], deck[2]……直到抛出 IndexError 异常为止。
同样，reversed(deck)（反向迭代）也是如此。如果没有 __reversed__ 方法，Python 会尝试利用 __len__ 和 __getitem__ 倒着取值，实现反向遍历。

3. 自动支持 in 运算符（Membership）

发生了什么？
我也没有写 __contains__ 方法，为什么可以用 in 来判断一张牌在不在牌堆里？
底层原理：
当 Python 执行 x in my_object 时，会找 __contains__。找不到的话，它会再次退而求其次，利用 __getitem__ 进行顺序扫描。
也就是说，它会通过 __getitem__ 把牌堆从头到尾拿一遍，挨个跟我找的那张牌比对，直到找到（返回 True）或者找完都没有（返回 False）。

(不过要注意，由于没有 __contains__，这种顺序扫描的效率是 O(n) 的，比起原生列表的 in 操作可能要慢。)

这是一个非常巧妙的加权打分算法：

举个例子：

  • 黑桃 A = 12 * 4 + 3 = 51（最大）
  • 红桃 A = 12 * 4 + 2 = 50
  • 黑桃 2 = 0 * 4 + 3 = 3
  • 梅花 2 = 0 4 + 0 = 0（最小）
    通过这个简单的数学算式实现了*“先比点数，点数一样比花色”    的规则。

二、 为什么是“组合”，而不是“继承”？

“虽然 FrenchDeck 类隐式继承 object 类，但是前者的多数功能不是继承而来的，而是源自数据模型和组合模式。”

基础不牢的喵喵，可能会喵：既然我是一副牌，里面装的是列表，我为什么不直接让 FrenchDeck 继承 list 呢？

  • 继承（Inheritance）：class FrenchDeck(list):。这样确实能直接用 append、pop 等等方法。但坏处是，它会把列表的所有方法都暴露出来。别人可以随便往你的扑克牌里加一个“苹果”或者“字符串”，这就不符合逻辑了。
  • 组合（Composition）：FrenchDeck 内部有一个 self._cards（是一个列表）。这叫把列表当作一个鱼干吃进自己的肚子里了喵。
  • 好处：你只挑你想要的特性（用 __len__ 代理长度，用 __getitem__ 代理拿牌）。别人不能改我肚子里的小鱼干————封装性更好。

四、 1.3 特殊方法是如何使用的（重点）

这一小节讲的是 Python 的底层逻辑和性能优化。

1. 有些新喵可能会直接调用 __len__
在写代码时，千万不要写 my_object.__len__()。
正确的写法是：len(my_object)。
为什么？因为 len() 是 Python 的内置函数（C语言实现的）。当你调用 len() 时，Python 解释器会直接去对象底层的 C 结构体（PyVarObject）里读取一个叫 ob_size 的字段（存着元素的个数）。这个速度超级快，比调用方法快得多。

2. for 循环
之前说过，你只写了 __getitem__，凭什么能 for i in x:？
书上解释了：for i in x: 背后其实是在调用 iter(x)。如果 x 没有 __iter__ 方法，Python 就会退一步，利用 __getitem__，从索引 0 开始，配合一个计数器，不停地去拿数据，直到抛出 IndexError。
(但注意：这种依靠 __getitem__ 的迭代是后备方案，效率不如直接定义 __iter__。)

3. __init__ 是个例外
绝大多数双下划线方法（比如 __len__、__getitem__）都是解释器偷偷调用的（隐式调用），但 __init__ 是个例外。
在写 deck = FrenchDeck() 的时候，其实是显式地触发了 __init__ 来给对象做初始化。这是代码编写中最常见的直接调用特殊方法的情况。

总结ing：

  1. 怎么用 sorted 的 key 配合自定义函数来实现复杂的多重条件排序。
  2. “组合（把对象装进去）”通常比“继承（变成子类）”更安全、更灵活。
  3. len() 为什么比调用 .__len__() 快（底层 C 语言优化），以及 for 循环如果没有 __iter__ 会怎么利用 __getitem__ 后位替代

1. __abs__ 的用法：
内置函数 abs() 本来是求绝对值的（比如 abs(-5) 等于 5）。对于向量来说，求“模长”（向量的长度）最合适了。所以当你写 abs(v) 的时候，Python 就去调用了 __abs__，里面用勾股定理（math.hypot）算出了向量的长度。

2. __bool__ 决定对象是“真”还是“假”：
在 Python 里，当你写 if v:，解释器怎么知道这个 v 是真还是假呢？
它会去找 __bool__ 方法。这里定义了：如果这个向量的长度（abs(self)）不是 0，那就是 True；如果长度是 0（也就是原点），那就是 False。

如果没写 __bool__ 怎么办？
Python 会接着找 __len__。如果长度为 0，布尔值就是 False。
如果 __bool__ 和 __len__ 你都没写，那么不管你类里装了什么，只要对象存在，布尔值就永远是 True。

当你写 if 某个对象: 的时候，Python 到底是怎么判断这个对象是 True 还是 False 的？

1.Python 的“降级判断”机制

对于你自己写的类（比如之前写的 Vector 向量类），如果你什么都不做，它默认就是 True。但很多时候我们希望它像列表一样，如果是空的（或者长度是 0），那就是 False。

书中讲了一个明确的优先级顺序：

  1. 首要：找对象里的 __bool__ 方法。优先
  2. 其次：如果没写 __bool__，Python 就去找 __len__ 方法。如果 len() 的结果是 0，就是 False；其他情况都是 True。
  3. 最后：如果这两个都没写，不管对象里装了什么，它永远返回 True。

3. or 的短路逻辑

self.x or self.y 返回了什么？

有些喵以为 or 返回的是 True 或 False。不对喵
在 Python 里，A or B 的底层逻辑是：

  • 如果 A 是真值（非 0，非空），直接返回 A 本身，后面的 B 直接咻的一声无了（这就是短路）。
  • 如果 A 是假值（0，空），再去算 B，并返回 B 本身。

举例子：

  • 如果 x = 3, y = 4，3 or 4 返回的是 3。
  • 如果 x = 0, y = 4，0 or 4 返回的是 4。
  • 如果 x = 0, y = 0，0 or 0 返回的是 0。

为什么外面要套一个 bool()？

因为 __bool__ 这个特殊方法有严格规定：它的返回值必须是布尔类型（True 或 False）。
如果你不套 bool()，直接写 return self.x or self.y，当 x=3 时，这函数会返回数字 3，会直接报错（TypeError: __bool__ should return bool, returned int）。
套上 bool(3) 之后，结果就被强转成了 True。

太喵了

利用了整数 0 就是 False 的特性。
只要 x 不是 0（比如是 3），直接返回 True
如果 x 是 0，那就看 y。只要 y 不是 0，就返回 True。

只有 x 和 y 都是 0 时，才会返回 False。

or 的返回值特性：它返回的是操作数本身，而不是单纯的布尔值。

UML类图

图 1-2 是一张 UML 类图，箭头代表“继承”（子类指向父类）。

1. 顶部三大奇喵接口

不管是什么容器，最基础的功能就这三个：

  • Iterable（可迭代）：里面写了 __iter__。只要实现了它，你的对象就能用 for...in... 循环遍历了。
  • Sized（有大小的）：里面写了 __len__。实现了它，你就能用 len(xxx) 知道里面装了多少个元素。
  • Container（容器）：里面写了 __contains__。实现了它，你就能用 if item in xxx: 来判断某个元素在不在里面。

2. “究极缝合怪”：Collection

注意看中间那个 Collection（Python 3.6 新增）。
它同时继承了上面三个。意思是，一个标准的“集合/容器”，天生就应该具备：能被循环、能算长度、能判断元素是否存在。

3. 底部

它们都继承自 Collection，是我们在写代码时最常用到的结构：

  • Sequence（序列）：代表有顺序的结构（如 list, tuple, str）。注意看它里面的方法，斜体的 __getitem__（可以通过索引取值，如 a[0]），还有不斜体的 index（找索引）、count（数个数）。
  • Mapping（映射）：代表键值对结构（如 dict）。它有 __getitem__（通过键取值，如 d['key']）、__contains__ 等。
  • Set（集合）：代表无序且不重复的集合（如 set）。里面有很多比较运算（__le__, __lt__ 等，对应小于等于、小于等集合关系）。

“斜体”与“鸭子类型”

书里图下面的第一句文字说明：

“以斜体显示的方法名称表示抽象方法，必须由具体子类实现。其他方法有具体实现，子类可以直接继承。”

  • 斜体字（如 __getitem__）：这叫抽象方法。如果要自己写一个 Sequence 子类，必须把 __getitem__ 写出来，不然没法用。
  • 非斜体字（如 index, count）：这叫具体方法。Python 底层已经用 C 语言或 Python 写好了。只要实现了斜体字的方法，这些非斜体字的方法直接拿来用就行

Python 的“鸭子类型”（Duck Typing）
书中有句话：“Python 不强制要求具体类继承这些抽象基类中的任何一个。”
在 Java 里，你可能必须写 class MyList extends Sequence。但在 Python 里，只要你看上去像鸭子，我就把你当鸭子。
只要你自己写的类里实现了 __len__，Python 就认定你满足 Sized 接口，你就能用 len()。不需要写任何显式的 继承(Sequence)。

表 1-2：运算符重载

1. 比较运算符

  • __eq__ (==), __lt__ (<), __gt__ (>): 比如 NumPy 里，a > 0 会返回一个由 True/False 组成的布尔数组，就是底层重写了比较运算符。

2. 算术运算符

  • __add__ (+), __sub__ (-), __mul__ (*)：最基础的加减乘。
  • __matmul__ (@) ：这是重点中的重点！
    这是 Python 3.5 才引入的专属矩阵乘法运算符。
    在 PyTorch 或 NumPy 里：
    • A * B 通常是逐元素相乘（Element-wise multiplication）。
    • A @ B 才是真正的矩阵乘法（Matrix multiplication，底层调用 __matmul__）。
      如果你自己写了一个简易的线性代数库，想让你的类支持 @ 乘号，你就得实现 __matmul__。
  • 还有一堆 iadd, isub（比如 a += b）：这叫增强赋值运算符，底层会优先尝试 __iadd__，如果没有，再退而求其次用 __add__。

反向、增量与位运算

这表里冒出来的 __radd__（Reverse Add）、__iadd__（Inplace Add）还有一堆位运算是什么东东？

1. 反向运算（__radd__, __rmul__ 等）

  • 假设你写了个类叫 MyVector。如果你写 v = MyVector(); print(3 * v)，Python 会先尝试调用左边整数 3 的 __mul__ 方法。但整数表示：“我不认识 MyVector，我不会乘”。这时候程序就会报错。
  • 如果在类里实现了 __rmul__（Right Mul），当 3 * v 报错时，Python 会反过来调用 v.__rmul__(3)。这就是书中说的“当第一个操作数没有相应方法时，退而求其次调用第二个操作数”。
  • 实战：在 PyTorch 里，不仅可以写 tensor * 2，也可以写 2 * tensor，就是因为底层张量类实现了反向乘法。

2. 增量赋值（__iadd__ 等，也就是 +=）

  • a += b 背后调用的是 __iadd__。
  • 它是区分“原地修改（In-place）”和“创建新对象”的关键。
    • 如果是列表：a += b 是就地拼接，内存地址不变。
    • 如果是张量：在 DL 里，weights -= lr * grad 是非常常用的优化器更新操作。了解这个机制，就知道有些时候张量的 += 可能会引发 RuntimeError（因为它在尝试原地修改一个被要求计算梯度的叶子节点，这在 PyTorch 里是被严格控制的）。

3. 位运算符（__and__, __or__, __xor__ 等）

  • 在 Python 里，集合（Set）的交、并、差底层用的就是这三个方法。
  • 在数据清洗或 Mask 操作中很常见。比如 PyTorch 里 tensor_a & tensor_b 做按位与操作。

第二部分：1.5 为什么 len 不是方法？

作者引用了 Python 核心开发者 Raymond Hettinger 的话，解释了为什么我们在用 len(x) 而不是 x.len()。

核心原因：为了极致的速度（C语言底层实现），以及内置方法的一致性。

  1. O(1) 的故事：len() 是一个内置函数，底层是用 C 写的。在一个内置类型（如 list, str, dict）上调用 len() 时，Python 不会去费劲地数一遍里面有多少个元素，而是直接去读取这个对象在 C 语言结构体里藏着的一个字段（ob_size）。所以不管你的列表有 10 个元素还是 1 亿个元素，len() 的耗时都是瞬间完成的（O(1) 时间复杂度）。

  2. 实用胜于纯粹（The Zen of Python）：如果把它做成方法 x.len()，虽然代码看起来更面向对象，但在 Python 庞大的代码库里，有些对象是内置的，有些是 C 扩展（比如 NumPy），有些是你写的 Python 类。为了保证所有人用起来都一样快、不折腾，统一使用内置的 len(x) 是最“实用”的做法。

杂谈 —— “数据模型”还是“对象模型”？

  1. Python 官方文档管这套机制叫 “数据模型（Data Model）”。
  2. 很多其他作者喜欢叫它 “对象模型（Object Model）”。
  3. 维基百科定义的对象模型是“编程语言中对象的一般特性”。
  4. 本书作者选择叫“数据模型”，单纯是因为官方文档就是这么叫的

不管你叫它数据模型、对象模型还是魔法方法，核心本质都是一样的——通过定义符合规范的双下划线方法，让你的代码融入 Python 的生态系统。
